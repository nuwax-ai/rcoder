git log 空分支误报错
“does not have any commits”

同事访问提交历史时，Java 返回 UNKNOWN_ERROR。 本质是工作区 git init 后尚无任何 commit，Rust 版空仓库兜底的字符串匹配写错了，把本应返回空列表的场景抛成了错误。

现象

git head_id: Branch 'refs/heads/main' does not have any commits

HTTP 响应包成 Java 平台错误壳：

{
  "code": "UNKNOWN_ERROR",
  "displayCode": "UNKNOWN_ERROR",
  "message": "git head_id: Branch 'refs/heads/main' does not have any commits",
  "success": false
}

一句话根因

gix 的未出生分支错误文案是 does not have any commits（没有 “yet”）， 而 Rust 兜底函数只认 does not have any commits yet（多了 “yet”）， 匹配失败 → 空仓库场景没有回落成空列表，而是原样抛错。

● 空仓库 / 空分支 ≠ 系统错误，应返回 commits: []

字符串匹配错位

gix 源码（thiserror 宏）与 Rust 兜底函数对照：

// gix/src/head/peel.rs
#[error("Branch '{name}' does not have any commits")]
Unborn { name: gix_ref::FullName }
// crates/file-server/src/service/git/read.rs:303
fn is_no_commit_error(e: &impl Display) -> bool {
    let msg = e.to_string().to_lowercase();
    msg.contains("does not have any commits yet")  // ← 多了 yet
        || msg.contains("unborn")
        || msg.contains("could not find")
        || msg.contains("not found")
}
匹配结果
实际消息 does not have any commits
期望子串 does not have any commits yet
→ contains() = false → 走 map_git_err 抛错

TS 原版为什么是对的

nuwax-file-server · gitService.js 正确
// 1) 预检：hasGitHead 解析 HEAD 失败 → 直接空列表
if (!(await hasGitHead(targetPath))) {
  return { success: true, commits: [], total: 0 };
}
// 2) catch 兜底：不要求 "yet"
/does not have any commits/i.test(msg)
rcoder · file-server (Rust) 偏移
// 只有 catch 兜底，且多了 "yet"
msg.contains("does not have any commits yet")
// 也没有 hasGitHead 等价预检

连带风险（顺手指出）

  • "could not find" / "not found" 匹配过宽， 可能把真实错误（对象缺失、路径越界）也吞成空列表，掩盖问题。
  • 注释写了「对齐 TS d1e5c8a: hasGitHead 预检」， 但实现里没有预检，只靠字符串兜底，脆弱且难测。
  • 更稳妥：用 gix 结构化错误 into_id::Error::Unborn / Kind::Unborn 判断， 而不是对文案做 contains。

推荐修复（file-server）

A. 修正字符串（最小改动，先止血）
把 "does not have any commits yet" 改成同时兼容两种写法，例如匹配 "does not have any commits"（去掉 yet）。 与 TS 对齐，立即可上线。 
// read.rs · is_no_commit_error
msg.contains("does not have any commits")
  || msg.contains("unborn")
  || msg.contains("unable to resolve")
B. 结构化判断（推荐跟进）
对 head_id() / rev_parse_single() 的错误按 gix 错误枚举匹配 Unborn， 或先用 repo.head() 判断 Kind::Unborn 再决定返回空列表。 避免文案漂移再次踩坑。 
// 对齐 TS hasGitHead 预检
match repo.head() {
    Ok(head) => match head.kind {
        gix::head::Kind::Unborn(_) => return Ok(Vec::new()),
        _ => {}
    },
    Err(e) if is_no_commit_error(&e) => return Ok(Vec::new()),
    Err(e) => return Err(map_git_err(e, "git head")),
}
C. 收紧兜底匹配
去掉过宽的 "not found" / "could not find"， 或改为精确的 gix/TS 错误码；否则真实缺陷会被吞掉。

必须补的测试

  1. 反例（修复前应失败）： git init 后 0 commit， 调 log_history(repo, 50, 0, None, None) → 期望 Ok(vec![])，当前会 Err。
  2. 带 branch 空分支： branch=Some("main") 且 main 无 commit → 同样空列表。
  3. 回归：有 commit 后 log 正常分页 / skip / file_path 过滤不被破坏。

业务侧规避（止血）

  • 工作区初始化后若业务允许，立刻做一次 initial commit（TS 的 addAllFirstCommit 路径），从源头避免 unborn。
  • Java 对 file-server 的「空仓库」语义可识别后转成空列表，但主修仍在 file-server。
