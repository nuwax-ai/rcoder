# UserApp prod `wake timeout` 根因分析(供修复方案分析使用)

- 日期:2026-09-19
- 环境:nuwax-k8s-test(192.168.1.18,swufe 免密),命名空间 `nuwax-k8s-test`
- 现象入口:前端 → Java(agent-platform)→ rcoder `POST /computer/pod/ensure?cId=1693329&appStage=prod`,app_id=104,返回 `ERR_BACKEND_ERROR: userapp prod ensure failed: wake timeout`
- 本文为纯分析产物,现场未做任何修改。所有代码引用以仓库当前 `feature-userapp` 分支为准。

## 0. 一句话结论

唤醒本身成功(scale 到 1),但应用容器已 17 小时 NotReady,rcoder 的 wake 60 秒等不到 `phase==Running` 报超时。NotReady 的根因是:**prod 链路的 PG 凭据从来没有送达应用进程;应用发布后 PG 角色密码被改掉,应用(只会用模板默认 dev/dev)从此连不上库;一次回收+唤醒后启动编排失败,落盘 failed 回执触发 app-cli 的 fail-fast 死角("interrupted after switch; explicit redeployment required"),永久拒绝自动拉起**。这是一个平台级链路缺陷,不是单应用偶发。

## 1. 因果链(每层均有实证)

### 1.1 wake timeout 的直接机制

- `crates/rcoder/src/handler/pod_handler/ensure.rs:200-225`:`ensure_userapp_prod` → `state.activity.ensure_running(&app_id)`
- `crates/app_manager/src/activity_registry/wake.rs:223-256`:single-flight 唤醒,leader 调 `wake_app_on_traffic`,预算 `wake_timeout` 默认 60s(`crates/rcoder/src/config/sections.rs:228` `default_userapp_wake_timeout_seconds`)
- `crates/app_manager/src/lifecycle/wake.rs:96`:`start_app_target` → `crates/docker_manager/src/runtime/k8s_app_lifecycle.rs:146-172` `start_captured_target` **仅 patch Deployment** `{"metadata":{"annotations":{"wake_on_traffic":"true"}},"spec":{"replicas":1}}`,不与容器内 app-cli 交互、不下发任何凭据
- 随后 `wait_for_captured_wake`(`lifecycle/wake.rs:134-187`)轮询 `fetch_runtime_status_or_err` 直到 `phase=="Running"`;Deployment 0/1 available → phase 永远非 Running → 60s 预算耗尽 → `WakeOutcome::Timeout` → 报文 "userapp prod ensure failed: wake timeout"
- 集群实证:rcoder pod 1 日志(2026-09-19 18:09:56、18:12:56 两次 `[POD_ENSURE] userapp prod wake timeout: app_id=104`,trace_id `95613e5c…`/`aca415b7…` 与 Java 收到的 tid 对应);Java 日志(31.101)确认 60 秒等待后原样透传

### 1.2 Pod 为什么 NotReady(17 小时)

- kubelet 事件:readiness probe `http://:3010/ready` 503 连续 6827 次(17h);liveness `:3010/health` 通过(容器 0 重启)
- 容器内实测:`curl :3010/health` → `{"status":"alive"}`;`curl :3010/ready` → `{"status":"not_ready","phase":"failed"}` (HTTP 503)
- app-cli 日志(`/home/user/logs/app-cli.err.log`,挂载卷持久):当前容器(2026-09-19 00:21 +0800 启动)启动即报
  `Deployment startup reconciliation failed error=deployment interrupted after switch; explicit redeployment required`
- 判定逻辑:`crates/app-cli/src/server_journal.rs:196-207` —— 容器启动时读取持久化部署回执,boundary 为 `Switching | Activated | Failed` 即 bail(fail-fast 防抖动设计:切换后启动未完成的代次不允许静默重试,要求显式重新发布)
- 现场 `/home/user/104/.deploy-operation.json`:`{"deploy_stage":"succeeded","boundary":"failed","phase":"failed","error":"deployment startup: deployment interrupted after switch; explicit redeployment required", …}` —— 部署本身成功过,但启动编排的回执落成了 failed

### 1.3 journal 为什么落成 failed

- 2026-09-18 06:14 UTC 唤醒:app-cli 编排启动 `app-svc-backend-go` 失败,`orchestration failed: start app-svc-backend-go: supervisord fault: {"faultCode":50,"faultString":"SPAWN_ERROR: app-svc-backend-go"}`(app-cli.err.log 原文)
- SPAWN_ERROR 的真实原因(容器内 `/home/user/logs/services/backend-go.log`):`./server` 启动即退出 ——
  `failed to initialize database ... failed SASL auth: FATAL: password authentication failed for user "dev" (SQLSTATE 28P01)`,重试两次均如此 → supervisord 拉起失败
- 该次失败的回执持久化后,后续所有容器启动撞上 1.2 的死角

### 1.4 PG 凭据为什么失配(根因)

四个事实叠加:

**(a) prod 容器 env 从来没有 `POSTGRES_*`。**
两代 Secret(`ua-104-12b6b761dea243b9-sec`、`ua-104-a01797e94c0a4323-sec`)的 data 均为空;ConfigMap 只有部署三元组(APP_DEPLOY_URL/SHA256/RELEASE_ID/OPERATION_ID/TOKEN);Deployment 直接 env 仅 APP_ID/PGDATA/DBX_DATA_DIR/USERAPP_WORKSPACE_DIR(两代 RS 均已核对)。应用进程拿不到平台凭据,只能用模板默认 `dev/dev`(backend-go 报错 `user=dev database=dev` 与之相符)。

**(b) PG 角色密码 = initdb 时的 env 值,此后不再跟随 env。**
prod 镜像 `build-agent-docker/build_config/app-runtime-base/pg-supervisor-entry.sh`:`POSTGRES_USER/PASSWORD` 默认 `dev/dev`,`PG_VERSION` 存在即跳过 initdb;PGDATA=/home/user/data/pg 在 PVC 持久化。即首次创建时角色=dev/dev,后续容器重启不改。

**(c) 发布时 rcoder 的 align 失败,且被静默降级。**
rcoder 操作库(rcoder-storage PG,`userapp_operations` 表)app 104 的 2026-09-17T03:18:55Z 发布记录(StartDeployment/cmd=deploy/state=Succeeded)中:
`"pg_error": "[ERR_INVALID_STATE] app 104 wake timeout (still starting in background), retry later"`,`pg_aligned=false`。
- 该错误来自 `crates/app_manager/src/runtime/db.rs:93-109` `ensure_app_running`:align 前置走与唤醒完全相同的 60s 等待;发布窗口内容器仍在下载制品/编排(未 Ready)→ 必然超时
- align 失败在发布链只降级为 `result.pg_error`(`crates/app_manager/src/lifecycle/deploy_control.rs:443-457`),部署照常 Succeeded;调用方(Java)未检查 `pg_aligned/pg_error`,静默吞掉

**(d) 发布后约 30 分钟,角色密码被改掉,应用不知情。**
PG 日志(`/home/user/logs/pg.err.log`)认证失败从 **2026-09-17 03:50:15 UTC(11:50 +0800)开始**,之前无任何 FATAL → 03:19-03:50 期间应用(dev/dev)连库正常。改密码的唯一通道是 align 的 `ALTER USER`(`shared_types/src/userapp/db_align.rs`,经 Java 的 reset/gen-db-credential HTTP 入口调用)。该 HTTP 路径**不产生 userapp_operations 记录**(align 不是 OwnedOperation),故 rcoder 操作表 03:50 无条目。实测 `PGPASSWORD=dev` TCP 连接失败,证实角色已是生成密码。Java 模型中 app 104 `prodDbPasswordSet=true`,佐证用户设置过 prod 数据库凭据。

### 1.5 dev / prod 链路不对称(缺陷本体)

- **dev 链**(Java `actionBodyWithPg` → file-server `dev_start`):`crates/file-server/src/service/dev_server/start.rs:331-340` 会把 `POSTGRES_USER/POSTGRES_PASSWORD` 注入 dev 服务进程 env,并对 dev PG align —— 凭据双向到达(PG + 进程)
- **prod 链**(Java `deployBody` 带 `pg` → rcoder `start_app_enhanced`):`request.pg` **仅用于 align(改 PG 角色)**(`lifecycle/deploy_control.rs:443`),从不进入容器 env,也从不通过 app-cli 运行控制协议下发。R08 设计的通道(`shared_types/src/userapp/runtime_control.rs:92-98` `OperationRunConfig.pg`,注释明确"用户更新的 PG 凭据经 Restart 到达编排的服务进程 env")在 K8s prod 的部署/重启/唤醒路径**从未被调用**——唤醒只是 patch replicas(`k8s_app_lifecycle.rs:169-171`),没有任何运行操作
- 因此:任何"用户改过 prod DB 密码 + 应用经历过一次回收再唤醒"的 UserApp,必然走进本文的死路

## 4. 修复方向(按优先级,供分析)

### 4.1 P0 平台缺陷:prod 凭据必须送达应用进程

与 dev 链对齐,prod 的部署/重启/唤醒链需把 PG 凭据送达应用进程,可选方案:
1. **容器 env 注入**:发布/改密时把 `POSTGRES_USER/POSTGRES_PASSWORD` 写入 app 的 Secret(`ua-<app>-*-sec` 目前为空,天然可用);容器重启后 app-cli 服务进程继承(需确认 app-cli `start_service` 对子进程 env 透传语义,`crates/app-cli/src/supervisor.rs:607-641` 现仅在有 `StartPgCredential` 时注入,R08 注释表明"运行时变量 last-wins 覆盖"——env 注入与该语义的优先级需设计)
2. **运行控制通道**:K8s prod 的 start/restart 走 app-cli `POST /v1/runtime/operations`(`RuntimeOperationRequest.run_config.pg`),唤醒路径在 scale-up 后补发 Start 操作携带凭据(改动较大,但语义上就是 R08 设计的本意)
3. 至少:**唤醒路径或 ensure 在检测到 `phase=failed` 且 error 含 "explicit redeployment required" 时,自动/辅助触发带凭据的重发布**

注意与既有设计的交互:dev/prod 凭据对齐契约(`shared_types/src/userapp/db_align.rs` 模块注释)、lock schema 变更需重建 app-runtime 镜像的约束(见 memory: app-runtime lock schema 漂移)。

### 4.2 P0:align 失败不得静默

- `deploy_control.rs:443-457` 的降级语义需要收敛:发布链中 align 失败应显式暴露给调用方(Java 检查 `pg_aligned/pg_error`,或 rcoder 直接把 align 失败作为发布失败/警示事件),否则凭据失配永远事后才爆
- `ensure_app_running` 前置在发布窗口内的时序问题:发布刚 scale 起来的容器天然未 Ready,60s wake 等待大概率超时。align 应在部署完成、容器 Ready 后重试,或对"刚刚由本次操作拉起"的场景直接信任执行(exec 到容器内执行 align 不依赖 Deployment Ready 判定,只要容器 Running 且 app-cli 3010 可达)

### 4.3 P1:journal failed 死角需要恢复闭环

- `server_journal.rs:199-207` 的 fail-fast 设计本身合理,但缺平台侧出口:一次瞬时编排失败(如应用自身启动失败)导致永久 "explicit redeployment required",而平台没有任何自动恢复或引导性报错。建议:
  - app-cli 侧:区分"部署切换中断"(危险,维持现状)与"启动编排失败"(可重试,如退避自动重试或允许重新编排);
  - rcoder 侧:ensure/wake 遇 `phase=failed` + 该错误时,返回精确错误(如 ERR_APP_DEPLOYMENT_INTERRUPTED + 提示重新发布),而不是笼统 wake timeout;
  - 可选:提供运维端点/接口完成"清 journal + 重发布"的恢复动作。

### 4.4 P1:wake/ensure 的错误分级

- `wait_for_captured_wake` 只认 `phase==Running/Error`,failed/dead-end 长时间 NotReady 全部表现为 60s 超时。建议在超时前查询 app-cli phase(`:3010/ready` 已提供 `phase` 字段)透出真实原因,便于前端和排障。

### 4.5 现场恢复(app 104/105,需人工,当前无 API 路径)

单纯"重新发布"修不好:redeploy 仍会带 pg 重跑 align(而 Pod NotReady → ensure_app_running 超时 → align 又失败;即便成功也只改 PG 不送达应用),应用依旧 SPAWN_ERROR。可行手工路径:
1. 容器内本地 trust 通道重置角色密码回应用已知值:`psql -h /var/run/postgresql -U dev -d dev -c "ALTER USER dev WITH PASSWORD 'dev'"`(本地 socket trust 免密;`db_align.rs` 的 alter 命令同款做法);
2. 清掉 failed 回执:删除或归档 `/home/user/104/.deploy-operation.json`(必要时连同 `.deploy-coordinator.json`),使下次容器启动走 Existing 编排而非死锁分支;
3. 删 Pod 让 Deployment 重建 → app-cli 重新编排 → backend-go 以 dev/dev 启动成功 → Ready;
4. 之后平台侧修复(4.1)落地前,**用户不要再在 UI 上修改该应用的 prod 数据库密码**;若必须改,需要同时保证应用侧同步(当前无机制)。
