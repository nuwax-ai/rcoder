# UserApp PG 原地改密（2026-09-20 修订）

## 已确认需求

用户明确选择：**立即改 PG，应用重启由用户决定**。本文件取代 CR10 中待生效配置、凭据换代、source-seal/helper/activation 的方案。历史事故分析及验证记录保留为历史证据，不作为继续开发这些协议的要求。

## 接口与行为

使用现有 `POST /api/v1/userapp/db/{app_stage}/reset-password`，按 app_id、dev/prod、lifecycle 和物理资源身份定位。运行账号允许直接修改。prod 容器未运行时明确返回错误，由用户先启动；不能为改密自动启动业务。

成功表示当前数据库的修改已提交，且指定凭据通过一次新的 TCP 连接验证。采用密码认证时，新密码用于后续新建或重连的连接。已有且已完成认证的 PostgreSQL 会话不因改密被主动断开，仍可执行查询；仅建立 TCP 但未认证不属于此保证。应用连接池可能暂时正常，在扩容连接或断线重连时才暴露旧密码。

接口不重启应用、不停止连接、不替换容器/Pod、不重新挂载 RBD，也不替用户修改业务连接配置。调用方自行更新业务配置，决定是否重启应用。

开发期新增的 `/api/v1/userapp/{app_id}/prod/runtime-configuration` 保存待生效接口退役。Java 保存入口继续使用实际改密接口，成功提示为“数据库密码已更新，请按需更新应用连接配置”。不回传密码。

## 实现边界

- 保留请求幂等、lifecycle/scope/物理身份核验和实际 SQL 结果未知时的恢复记录；HTTP 断开不能伪造成功或放行未知操作。
- 取消保存配置触发的源封存、辅助 Pod、Secret 换代、启动 activation gate。
- 普通启动、重启、自动唤醒不读取历史待生效密码，不把数据库密码改回旧配置。
- 显式部署请求自身携带 pg 时，只使用该请求的确定输入，不生成待生效配置，不仅因 pg 触发容器换代。
- PGDATA 初始化管理员身份与用户可修改的业务账号继续分开。既有数据卷不按默认环境变量重设密码。
- 不清除历史未知操作或损坏 journal 来规避恢复保护。普通镜像/资源更新的身份和卷保护继续保留。

## 验收断言

1. 预先用旧密码建立并认证会话，改密后同一会话查询成功。
2. 新建连接用新密码成功；启用密码认证的新连接用旧密码失败。
3. 改密前后 prod 物理 UID、业务 owner 不变，没有停止业务、终止连接或创建辅助容器。
4. 同 app 的 dev 数据库不受 prod 改密影响。
5. 普通显式重启/自动唤醒不重放历史保存密码；重启后数据库仍接受新密码。
6. 停止的 prod 改密明确失败，不隐式唤醒。
7. SQL 已提交但网络断开的未知结果沿原请求身份恢复，不生成新身份盲目重复。
