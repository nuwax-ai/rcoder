# Spec：自包含的三平台桌面运行时

## 1. 目标与范围

`app-cli` 和 `file-server-proxy` 均支持 Windows、macOS、Linux 原生运行，可独立使用，也可作为 Electron 的原生配套组件。宿主机不需要安装或启动 Docker、K8s、supervisord、RCoder 服务端、PostgreSQL、Redis 等后台服务，才能使用产品基础能力。

两者的职责保持清楚：

| 组件 | 负责 | 对另一组件的依赖 |
|---|---|---|
| app-cli | 应用运行态的唯一所有者；编排、启停、激活、代理入口和恢复 | 不要求 file-server-proxy 或 Electron 存活 |
| file-server-proxy | 内嵌 Rust 文件服务；文件/Git/构建任务接口；调用 app-cli 控制 UserApp | 基础文件服务不依赖 app-cli；应用运行功能按需发现或启动 app-cli |
| 后续 Electron 等调用方 | 定位随包二进制、连接控制接口 | 本轮只定义组件侧契约，不开发客户端 |

不能引入新的“桌面总控服务”作为启动两组件的前置。允许它们以当前用户的普通进程运行；安装系统服务不是前提。

## 2. 自包含的边界

| 类型 | 要求 |
|---|---|
| 基础能力 | 文件读写、目录/Git 本地操作、任务与日志、owner 管理、已具备运行条件的应用启停及静态预览，不强制连外部后台服务 |
| 产品内部组件 | Rust 文件服务进程内集成；Pingap 等必要可执行组件随对应平台包携带并私有托管，不要求用户预装 |
| TypeScript 文件服务 | 原生标准模式不依赖、不自动启动。已有 TS 兼容模式显式选择并保留边界；不得静默回退 |
| 项目工具链 | Node/pnpm、Java、Python 等是具体项目的能力前置；支持已配置工具路径或产品随包工具链，缺失时说明具体工具与阶段 |
| 项目数据库 | 只有项目明确需要时才连接并检查；可连接用户配置的数据库。应用确实要求 PostgreSQL 时，不能以“自包含”为由伪造成功或擅改成 SQLite |
| 网络与安装 | 已安装完整包的基础启动及本地离线夹具不应触网补下载；首次产品安装、项目依赖下载、Git 远端、AI/远端数据库操作另计 |

基础原生二进制运行不依赖全局 Node。npm 安装入口自身需要 Node/npm，不等于 Electron 成品使用者必须安装它们。支持 JavaScript 构建时可提供私有 Node/pnpm 工具链；不要求将所有语言工具链与数据库都塞进首版基础包。

原生标准模式启用 Rust 路由前，须核对原有必需 API 的覆盖。缺失的必需功能继续开发；显式返回 unsupported 可以防止假成功，但不代表功能完成。

## 3. 平台与形态

基础目标：Linux x64/ARM64、macOS x64/ARM64、Windows x64，两个组件使用同一份明确的支持清单。Windows ARM64、Linux musl 等额外目标分别核验配套组件，不能因其中一个包能构建就宣称整套支持。

原生模式使用 builtin 进程管理；现有容器模式继续兼容既有托管器、固定端口及平台身份配置。操作系统和部署模式分开：Linux/macOS 的 Unix 编译分支不意味着处在容器中。

## 4. 生命周期及所有权

- 同一规范项目只有一个 app-cli owner；Electron、CLI、file-server-proxy 使用同一身份、状态根、操作协议。改端口、打开第二个窗口、切换客户端配置均不能产生第二个 owner。
- 不同项目可以并存。file-server-proxy 的实例范围须明确，默认按本地客户端配置空间复用一个实例；不能继续使用不区分范围的临时目录全局 PID 文件。
- 操作身份、幂等、revision、Stop 屏障、事件重放及恢复保护继承运行态所有权 Spec。构建者只提交 staging，owner 才能激活运行目录。
- 客户端断连不是用户 Stop。原生后台模式保留 app-cli 的业务运行；显式 Stop 持久化 Stopped。具体客户端的退出策略由客户端后续决定，并通过同一控制协议执行。
- 组件退出与业务 Stop 分离。file-server-proxy 退出不停止由 app-cli 托管的业务；其自有构建子进程要取消并确认，或依据已有持久任务协议恢复，不能悄悄遗留。
- 前台 CLI 的中断必须经过明确停机路径；附着客户端退出仅解除会话，不能杀掉复用的 owner。升级也使用相同的身份和停机边界。
- 无法确认业务树退出或执行结果时保留保护，不能以 PID 消失、监听关闭、时间经过代替确认。

## 5. 路径、端口与本机接口

- 产品资源目录只读；状态、凭据、日志、缓存分别放当前用户可写目录，状态不依赖系统临时目录。工作区由用户选择，不要求 `/app`、`/run`、管理员权限或系统级目录。
- 项目身份不能只是 basename、任意字符串路径 hash 或默认 `unknown-app`。处理 source/.run、符号链接、junction、大小写及项目移动/复制的区别。
- 管理地址和文件 API 默认只监听 loopback，并认证、核验组件/实例/项目身份。两者的凭据相互区分，不进入 renderer、URL、日志、预览页面或普通事件。
- 原生管理口与文件服务入口支持真实动态端口；Pingap admin、业务入口及项目服务端口共同规划。固定端口已占用要明确失败，不能杀占用者或静默改用户约定。
- 本机文件接口保留已授权的路径能力；对调用方传入的任意目录、`customTargetDir` 等参数核验权限。loopback 与 CORS 都不能替代授权。
- 本地 OS 用户隔离不重新引入已退役的业务 `user_id`/`x-user-id`。

## 6. 分发与外部程序调用

- 组件可由外部程序直接启动，支持明确的二进制路径、参数数组、cwd/env、身份/就绪查询及停止接口；不用终端输出文案作为机器协议。
- 原生分发包包含对应 OS/架构的版本锁定产物、配套文件和校验信息；不能依赖开发机器的 node_modules、全局 PATH 或第一次运行时联网补齐。
- 组件版本切换处理活动任务、旧 owner、Windows 可执行文件占用和协议兼容；不原地覆盖运行中的二进制，不清空 journal。
- 三平台分别做真实原生进程测试。Electron 的 UI、IPC、签名、安装器和自动更新属于客户端后续工作，本轮不开发，也不以原生测试宣称客户端验收完成。

非目标：首版不实现任意项目自动转换为跨平台脚本、不内置全部数据库、不安装系统服务、不承诺恶意程序或管理员绕过机制后的隔离，不为单一可执行文件目标重写全部 Pingap 配置语义。
