# Spec：UserApp 运行态单一所有者

## 1. 问题与证据边界

同一 builder 中，平台 legacy dev 编排与 AI/用户启动的常驻 serve 可以同时存在。它们争用管理 API、pingap 入口和代理 admin 端口，也可能修改相同运行目录。supervisord 自动拉起使杀单个进程无法可靠解除冲突。

当前源码还存在错误传播断层：API 绑定错误仅记录；部分启动错误跳过最终事件；legacy main 吞掉 supervisor 错误；stdout EOF 不上报；调用方保留事件发送端。最终任务可能在实际编排已失败后继续等待。

用户材料中的线上版本、端口占用、时间线是事故输入。HEAD 的 25 秒代理确认预算已由源码确认，但不据此宣称线上进程确在某秒退出；历史结论需要事故二进制身份和完整日志支持。

## 2. 范围

### 包含

- UserApp `/api/v1/userapp/dev/*` 的启动、重启、停止、列表以及关联任务取消和 SSE。
- app-cli legacy 与 serve 的启动错误传播；serve 的统一运行操作内核。
- builtin 与 supervisord 两种服务托管器下的 dev/source 和 artifact 语义。
- 稳定状态根、操作记录、实例身份、幂等重放、事件重放和重建恢复。
- builder 启动配置及新旧控制者迁移；必要的生产热部署适配与回归。

### 非目标

- 不做按端口杀占用者、按名字清空所有 app-cli、自动删用户 supervisor program。
- 不在本轮实现零停机、蓝绿或只重启变更服务的增量部署。先保持整组切换。
- 不合并 UserApp builder 与生产容器的资源生命周期，不改变 agent PVC 保留规则。
- 不重做 Custom Page/Web 单 Vite 协调器，不向独立 file-server 注入 PG/K8s 依赖。
- 不禁止 AI 执行 shell、不承诺抵御 root 主动绕过协议；身份和锁用于协作正确性，不是 root 安全边界。
- 不提供任意迁移脚本/数据库变更的自动回滚，不用 mock AI 代替真实 AI 验收。

## 3. 强制不变量

| ID | 要求 |
|---|---|
| R01 | 同一应用运行环境只有一个运行态所有者；源码路径、`.run`、符号链接别名不得形成独立锁域 |
| R02 | 任何修改运行态的路径使用同一操作内核；目录激活、停止、重启、恢复不能绕过 |
| R03 | 身份/锁及 API bind 成功后才允许运行态副作用；失败不能停止其他实例的服务 |
| R04 | 结果属于明确 operation、实例和目标版本；旧端口可访问不等于本次启动成功 |
| R05 | 接受操作前持久化；终态发布前持久化；未确认停写/停进程保持恢复保护 |
| R06 | HTTP/SSE 观察者断开不取消执行所有权；未知结果不释放互斥、不启动第二轮 |
| R07 | 重复 operation ID 相同请求返回原结果；不同请求明确冲突，不能重复迁移/重启 |
| R08 | stop 意图阻止先前受理的构建在稍后重新启动应用；重建不得复活已明确停止的应用 |
| R09 | devrun/devbuild 与制品运行均保留；源码模式不强制生成 zip、不替换源码根目录 |
| R10 | 服务事件有序且先于任务终态；断线可重放；启动失败、EOF、退出、超时分别可诊断 |
| R11 | 新协议超时、身份不符、403、能力缺失不能触发旧 spawn 回退 |
| R12 | 只清理本轮持有且可证明归属的资源；无法确认的清理结果不能作为重试放行依据 |

## 4. 对外行为

### start / restart / deploy / stop

- `start` 是确保运行。已经运行则保持现有版本，返回有效版本身份；保持现有 dev/start 不隐式发布新构建的语义。
- `restart` 在平台原有构建策略完成后重新编排；artifact 输入可更新有效制品，source 输入保留开发命令。
- `deploy` 是显式替换制品并编排；不允许将部署端点用于替换源码工作区。
- `stop` 持久化 Stopped 意图，取消/阻止旧启动提交，停止业务服务与业务入口，管理进程保持可用。
- `status/list` 返回实际运行状态；控制进程活着不能被表示成业务已运行。旧 PID 字段只能是真实兼容信息，不能作为以后杀进程的授权。
- build 单独运行不启动应用；构建可能修改源码产物，不能被描述成完全无文件副作用。

### 错误与完成

- 启动失败包含阶段、错误码、应用/操作/实例身份、目标版本、最后进度和清理结果。
- PID、可识别的 supervisor program、端口、脱敏日志尾部是诊断信息，不是抢占授权。
- 敏感 argv/env/token 不出现在错误响应；PID/命令获取不到时保留原始错误，不让诊断失败掩盖根因。
- 执行状态未知与确定失败不同。对旧 UI 可保留 Failed 事件名并提供明确错误码/operation ID，但后端不可因此释放运行态所有权。
- 首期保留 legacy 的服务探针失败可留下部分运行服务的行为；任务失败不伪装全部停止。阶段二统一操作结果须明确运行健康及清理状态，不能偷偷改变为全组强杀。

## 5. 期望状态与恢复

- 区分 desired state（Running/Stopped）、operation result（成功/失败/取消/待恢复）、observed health。
- 重建只自动恢复已经确认的有效运行目标，并服从最新 desired state。
- Switching 等中断边界、损坏记录、未确认旧进程退出保持待恢复，不猜测回滚。
- source 恢复使用持久化工作区当前内容，必须重新校验配置、依赖和运行计划；不宣称可重现旧源码快照。
- 正常控制进程关停与用户 stop 不同：前者可保留 Running 意图用于容器重建恢复，后者必须持久化 Stopped。

## 6. 完成范围

- 阶段一：错误不再只表现为等待最终事件超时，且正常/慢启动/取消不退化。
- 阶段二：两种托管器使用统一受理、记录和运行控制；正常 CLI 行为幂等协作。
- 阶段三：平台全部 dev 生命周期入口迁移并验证真实 Compose/K8s；旧链路不能旁路写入。
- 每阶段以本轮源码、测试命令、退出码、镜像 digest 和报告证明；源码核对、组件测试、真实部署、发布分别报告。
