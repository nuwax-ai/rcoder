# Builder 条件清理边界

UserApp 的独立 Dev storage destroy 与生产 purge 均先捕获 builder 物理资源，再执行删除。生产 purge 必须在生产资源副作用之前捕获此凭据。捕获后持有应用级操作租约；Docker 删除使用容器 ID，Kubernetes 删除使用 UID 与 resourceVersion 前置条件，等待 StatefulSet 前台删除完成后才删除原 PVC。API 查询失败、资源替换或版本冲突均中止，不继续清目录或注册表。

权威查询不存在且注册表不存在时，重复清理可以幂等成功。若注册表仍存在但缺少容器身份，清理会明确失败；不能退化为按 app_id 或仅 generation 删除，因为另一个副本可能在稍后登记同一代次的新容器。此时应先核对 runtime 真实资源、注册表所属族和持久化关联，恢复其准确身份后再重试。恢复过程不自动删除未知资源或用户数据。

Kubernetes 操作租约不采用 TTL 偷锁。进程异常退出留下的租约，需要先证明旧写入者不再执行，再由运维按租约自身 UID/resourceVersion 清理；不能仅凭时间到期认为安全。正常请求取消不会中断已经受理的创建或清理 worker，资源操作结束后释放租约。

本轮验证为本地组件和 Kubernetes HTTP API 契约适配器，不代表真实集群验收。真实多副本、存储 provisioner 和前台 GC 时序仍应在个人开发集群后续验证。

Docker 使用同一 `.app-operation-locks` 目录下按服务族分离的文件和共享 `AppFileMutationMarker` 协议。创建、删除或清理结果不确定时，即使文件描述符已经释放，持久标记仍阻止后续操作；只有明确完成才核对操作 UUID 并清标记。只读捕获被正常取消会主动清标记；捕获阶段进程崩溃同样可能留下标记，需按上述“先证明旧写入者静止”的流程恢复。已确认无副作用的身份、资源参数、服务配置和镜像选择预检在获取租约之前完成；这些预检失败可修正配置后直接重试。实际容器创建 worker 返回错误不会自动解锁未知结果；不能用盲目重试绕过保护。
