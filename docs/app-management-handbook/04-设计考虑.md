# 4. 设计考虑

> 本章解释"为什么接口长这样"——每个决策的动机和对调用方的影响。
> 想深究完整决策依据（对标调研、CRD 取舍），见 [v2 设计文档](../application-management-service-v2-design.md)。

---

## 4.1 根本出发点：RCoder 是"无状态的应用 Pod 引擎"

一句话贯穿所有设计：**RCoder 进程不持久化任何应用元数据。**

这条约束带来三个直接后果，理解了它们，后续每个设计都不言自明：

1. **读路径必须现场从集群重建**——没有缓存可读，每次 `GET` 都实时查集群。
2. **RCoder 重启不丢应用**——所有托管资源都打了 `managed-by=rcoder-app-manager` 标签，重启后 label 反查即可重建 observed 视图，无需任何恢复动作或本地 DB。
3. **desired state 的 source of truth 是 Java**——RCoder 只在 create/update 时短暂持有 desired（用完即弃），读时拿不到业务字段（name/image/env），所以 `GET /apps/{id}` 只能返回 observed。

> 代价是诚实的：`GET /apps/{id}` 不含 `image`/`name`/`env` 等业务字段。需要合并视图由 Java 自己拼（DB desired + RCoder observed）。这是"无状态"换来的简单性与可恢复性，刻意取舍。

---

## 4.2 为什么只允许 GET + POST（写操作动词进 path）

**约束来源**：RCoder 部署在生产环境的网关只放行 `GET` 和 `POST`，禁用 `DELETE`/`PUT`/`PATCH`。

**应对**：把写操作的动词直接放进路径——`POST /apps/{id}/delete`、`POST /apps/{id}/update`、`POST /apps/{id}/files/delete`、`POST /apps/{id}/storage/delete`。读用 GET，写用 POST。

> 这不是 RCoder 的偏好，是部署环境的硬性限制下的标准做法。对调用方无额外负担——HTTP 方法语义明确，URL 自解释。

---

## 4.3 为什么创建是异步的（不等 Ready）

`POST /apps` 创建完所有资源后**立即返回**（`status` 通常为 `Starting`），**不阻塞等 Pod Ready**。Java 通过轮询 `GET /apps/{id}` 观察 `Starting → Running`。

**为什么**：多语言镜像 pull + 启动可能耗时数十秒到分钟级。同步阻塞会占满连接池、触发网关超时。而 **Deployment 本身就是天然的异步状态机**（replicas / readyReplicas 随时可查），用它承载"异步"即可，**不需要额外的任务表**。

> 对比 Epinio 用 in-memory map 存异步部署状态——重启全丢，是真实弱点。RCoder 把异步状态交给集群（Deployment.status），自己保持无状态。

**对调用方**：创建后必须轮询，别假设返回即就绪。轮询建议：间隔 2–5s，关注 `status` 与 `conditions[].reason`。

---

## 4.4 为什么 update 是"全量替换"而非"部分更新"

`POST /apps/{id}/update` 的语义是**全量替换 desired state**——调用方必须发送完整新状态，**`image` 必填**。

**为什么**：RCoder 无状态，**不持有旧 desired**，无法做"未传字段保留旧值"。例如你想改 `env`，RCoder 并不知道旧 `env` 是什么，只能让你把完整新 `env` 传进来。

**幂等保障**：K8s 后端走 Server-Side Apply（SSA）re-apply——同一请求重复发，结果一致，create-or-update 自然合一，每个字段有独立 field manager 互不误伤。Docker 后端无 in-place 更新，image/env/command 变化触发容器重建（但保持容器名不变，路由/端口尽量复用）。

**对调用方**：update 时把整个 desired（image + command + env + secrets + resources + ports + health_check）都带上，当成"用新配置重新部署"。这与 Java 作为 desired state source of truth 的定位一致——Java 本来就持有完整 desired。

---

## 4.5 为什么删除默认保留持久数据

`POST /apps/{id}/delete` 默认**只删计算面**（Deployment/Service/路由/ConfigMap/Secret），**保留数据面**（code/data/logs 目录）。需要连数据清，传 `purge: true`。

**为什么**：**应用可重建，数据不可再生**。误删应用若连带抹掉 `data/`（数据库、用户上传、文件日志）是灾难性的。

**实现保障**：持久存储是共享 PVC 上的 `apps/{app_id}` 目录（K8s）或 `app-workspace/{app_id}/`（Docker），它**不是 K8s 计算资源，不在 label 扫描范围**，因此 delete 的 orphan 扫描天然不会误删它——"默认保留"是有实现保障的，不是偶然。

**对调用方**：
- `delete` 后数据仍在；用同一 `app_id` 重新 `POST /apps` 会自动挂回旧数据（适合"误删找回"）。
- 想要干净起点：先 `delete`（保留数据）→ 确认无误 → `POST /apps/{id}/storage/delete`；或直接 `delete` 时传 `purge: true`。
- `storage/delete` 有安全约束：**仅当 app 已 delete（计算资源不存在）时才允许**，否则 `409 ERR_INVALID_STATE`，避免清空在用数据导致损坏。

## 4.6 状态机

`AppStatus` 由集群 phase 实时映射派生（不是 RCoder 自己存的状态机）：

```
                ┌──────────────────────────────────┐
                ▼                                   │
POST /apps → Starting ──ready≥1──→ Running ──scale0──→ Stopped
                │                     │                   │
                │                  rollout              scale1
                │                     ↓                   │
                │                  Starting              │
                │                                         │
              fail(crash/image)                          │
                ↓                                         │
              Error ───POST /update(修 image/env)─────┘
                │
          POST /delete
                ↓
             Deleting ──GC完成──→ (404 ERR_APP_NOT_FOUND)
```

phase → status 映射（`phase_to_status`）：

| 运行时 phase | AppStatus |
|---|---|
| `Running` | `Running` |
| `Stopped` / `ScaledDown` | `Stopped` |
| `Starting` / `Pending` / `Creating` | `Starting` |
| `Error` / `Failed` | `Error` |
| 其他（兜底） | `Created` |

**关键**：`status` 给 Java 做状态机判断（粗粒度、稳定）；`conditions[]` 给人/前端做细粒度诊断（含 `reason`：`CrashLoopBackOff` / `ImagePullBackOff` / `ScaledDown` 等）。二者同源派生，不矛盾。

---

## 4.7 对账机制（重启恢复，无状态核心）

RCoder 进程重启后：

1. **不需要加载任何本地状态**（本来就没有）。
2. Java 调 `GET /apps/runtime` → RCoder label 反查所有 `managed-by=rcoder-app-manager` 的 Deployment，对每个返回 `AppRuntimeInfo`。
3. Java 对照自己的 DB 做差异：
   - **DB 有、集群没有** → 重新 `POST /apps`（desired 由 Java 持有，可重建）。
   - **集群有、DB 没有** → `POST /apps/{id}/delete` 或保留（Java 业务策略）。

这条链路**完全靠 label + 集群 API，不需要任何额外存储**。这是"无状态引擎"的核心优势，也是与"声明式 CRD controller"路线的根本区别。

> 数据侧对账用 `POST /apps/storage/query`（`orphan_only: true`）——与 `GET /apps/runtime` 互补，合起来覆盖"应用 vs 数据"两侧。

---

## 4.8 文件路径契约：app 根相对 + path traversal 防护

所有文件接口（`upload` 的 `target`、`files` 的 `path`、`files/delete` 的 `path`、`logs/file` 的 `path`）**一律 app 根相对**（如 `code/app.jar`、`data/db/`）。

**三层防护**（纵深防御）：

1. **app_id 格式校验**：app_id 直接来自 URL 路径参数并流入文件路径拼接。RCoder 严格校验 `app-` + 8 hex 格式，拒绝 `..`、绝对路径、非法字符（→ `400 ERR_VALIDATION`）。
2. **canonicalize + starts_with**：对目标路径 canonicalize 后校验仍在 app 根目录内，拦截 `../../` 上跳。
3. **绝对路径拦截**：`PathBuf::join` 遇绝对路径会替换基准，RCoder 在 canonicalize 阶段一并拦住。

> 对调用方：路径始终用 app 根相对形式，不要传绝对路径，否则被拒。返回的 `files[].path` 也是 app-root-relative，可直接复用为 target/path。

---

## 4.9 为什么日志流用 WebSocket 而非 SSE

`GET /apps/{id}/logs/stream` 用 **WebSocket upgrade**，服务端逐行推送 `LogEntry` JSON。

**为什么 WS 不是 SSE**：

- **双向**：Java 可主动发控制帧（如停止 follow、切换 tail）；SSE 是单向的。
- **与后端一致**：K8s（kube-rs `log_stream`）、Docker（bollard `logs(follow=true)`）自身的日志流都是双向的，WS 桥接最自然。
- **断开即停**：客户端断开 → handler 退出 → mpsc receiver 析构 → 后台 follow 任务自动终止，无泄漏。

**快照与流式分离**：
- `GET /apps/{id}/logs` —— 历史快照（一次性返回 `Vec<LogEntry>`，适合排查已发生的问题）。
- `GET /apps/{id}/logs/stream` —— 实时 follow（适合"盯着日志看"）。

> 还有一个 `GET /apps/{id}/logs/file`：从工作空间 PVC 的 `logs/` 目录直接读文件，适用**不写 stdout 而写文件**的应用（Java Spring Boot 的 `logs/application.log` 是典型场景），不依赖容器 log API。

## 4.10 为什么存储信息不含 size_bytes

`StorageInfo` 只有 `{ app_id, exists, path, modified_at, is_orphan }`，**刻意不含 `size_bytes`**。

**为什么**：app 存储落在共享 CephFS PVC 上（per-app subPath）。在 CephFS 上**每次 `stat`/`du` 都是一次到 MDS 的网络往返**，递归遍历目录树代价极高、会压垮 MDS。RCoder 绝不用 `du` / 递归 stat 算 size。

**per-app 存储用量交给 Ceph 原生体系**：
- 观测：`ceph-mgr` + Prometheus `ceph_exporter` + Grafana。
- 限额：CephFS 每目录配额 `ceph.quota.max_bytes`（`setfattr -n ceph.quota.max_bytes -v <bytes> <dir>`）。

这样 RCoder 既不算 size，也不背存储计费的锅。

> 查询接口 `POST /apps/storage/query` 因此是**强制分页、无全量模式**（`page`/`page_size` 必填，上限 100），且只单层列工作空间目录、每条 O(1) stat，规模可控。
>
> 备选（未来）：CephFS MDS 内置维护每目录递归大小，可读虚拟 xattr `ceph.dir.rbytes`（一次 `getfattr`，O(1)、不遍历），仅在 `GET /apps/{id}/storage` 单点实现；列表接口无论如何都不算 size。当前不做。

---

## 4.11 服务暴露：为什么 RCoder 只返回 path，host 交给 Java 拼

**统一原则**：无论 Pingora（默认）还是 gateway（可选），`access.external.http` **都只返回 path**（`/proxy/{port}` 或 `/apps/{app_id}`），host 由 Java 拼。

**为什么**：客户端要通过 RCoder（Pingora 模式）或 gateway（gateway 模式）才能访问应用，Java 必然已持有该入口地址——否则请求进不来。RCoder 再返回完整 URL 是冗余，还会引入对外部域名的配置依赖（多环境生产/预发/租户域名不同，耦合重、易错）。只返 path、host 交 Java，最干净。

**对调用方**：Java 用自己已知的入口（Pingora 模式 = RCoder 入口；gateway 模式 = gateway 域名）+ RCoder 返回的 path 拼出最终 URL。两种模式拼接逻辑完全一致。

## 相关设计取舍（速览）

| 设计点 | 选择 | 否决的方案 | 原因 |
|---|---|---|---|
| 是否引入 CRD + controller | **不引入**（命令式无状态） | App CRD + reconcile loop | 与无状态定位冲突、破坏 Docker 对称性、与 Java desired 权威打架、复杂度数倍 |
| 删除是否含数据 | **默认保留** | 默认连数据删 | 数据安全优先（数据不可再生） |
| update 语义 | **全量替换 + SSA** | 部分更新 | 无状态无法保留旧 desired；SSA 保证幂等 |
| 异步状态承载 | **Deployment 自身状态** | in-memory job map | 重启不丢、无需额外存储 |
| 日志流 | **WebSocket** | SSE | 双向、与后端一致、断开即停 |
| 资源 GC | **label 扫描 + orphan 清理** | OwnerReference | 后端无关（Docker 也能用），不需父 CRD |

完整决策记录见 [v2 设计文档](../application-management-service-v2-design.md)。
