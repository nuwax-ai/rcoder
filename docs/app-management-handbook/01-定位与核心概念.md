# 1. 定位与核心概念

> 本文是阅读后续接口手册前必须先建立的心智模型。读完你会清楚：RCoder 是什么、它**故意不做**什么、你和它各负责什么。

---

## 1.1 一句话定位

> RCoder 是一个**无状态的应用 Pod 引擎**：你给它一个容器镜像和启动参数，它把这个镜像跑成一个可被访问的长期运行服务，并实时回报它的运行状态。

它面向的调用方是 **Java 业务服务**（不是终端用户、不是前端）。Java 负责管理"应用的业务元数据"（叫什么名、镜像是啥、谁创建的、什么时候创建的），RCoder 只负责"把它跑起来、查它的实时状态"。

---

## 1.2 决定一切设计的两条根本约束

这两条约束贯穿所有接口，理解它们就理解了为什么接口长这样。

| 约束 | 含义 | 对你（Java）的直接后果 |
|---|---|---|
| **RCoder 进程无状态** | RCoder 不持久化任何应用元数据；进程重启后内存全空，但它能从集群里重新"发现"正在跑的应用 | 读接口是**现场从集群重建**的，不读缓存；RCoder 重启不丢应用，你也不需要做任何恢复动作 |
| **应用元数据归 Java 持久化** | name / image / created_at / 业务标签这些"业务字段"存在 Java 的 DB 里，RCoder 不存 | RCoder 的响应分成两类：**desired（来自你的请求）** 和 **observed（来自集群）**，二者职责分明，见 §1.3 |

一句话：**RCoder 是"命令式 + 现场观测"的引擎，不是"声明式对账"的控制器。** 你发命令、它执行；你查状态、它现场读集群告诉你。

---

## 1.3 desired 与 observed：两套数据，别搞混

这是最容易踩坑的地方。RCoder 的数据严格分成两套：

```
   ┌─────────────────────────┐         ┌─────────────────────────┐
   │  desired（你想要的）      │         │  observed（集群里实际的） │
   │  来源：你的请求体         │         │  来源：实时查集群         │
   │  归属：Java 持久化        │         │  归属：RCoder 现场组装     │
   │  例：image=java:17,      │         │  例：status=Running,     │
   │      replicas=1, env=... │         │      ready=1, pod_ip=... │
   └────────────┬────────────┘         └────────────┬────────────┘
                │                                    │
                │   只有 create / update 时 RCoder   │
                │   才短暂持有 desired（用完即弃）    │
                └────────────────┬───────────────────┘
                                 ▼
                      创建/更新时合体返回 AppInfo
                  读路径只返回 observed（AppRuntimeInfo）
```

| 数据 | 在哪个响应里出现 | 字段举例 |
|---|---|---|
| **desired** | 仅 `POST /apps`（创建）与 `POST /apps/{id}/update`（更新）的响应 `AppInfo` / 回显 | `image`、`command`、`env`、`name`、`resources` |
| **observed** | 所有读路径返回的 `AppRuntimeInfo` | `status`、`phase`、`ready_replicas`、`pod_ip`、`ports`(实际对外端口)、`access`、`conditions` |

> ⚠️ **重要**：`GET /apps/{id}` **只返回 observed（`AppRuntimeInfo`）**，不含 `image` / `name` / `env` 这些业务字段。
>
> 为什么？因为 RCoder 无状态，它读时不知道你当初传的 desired 是什么——只能从集群现场读"现在跑成什么样了"。如果你需要"desired + observed 合并视图"，**由 Java 自己用 DB 里的 desired + 调 RCoder 拿到的 observed 合并**，这是刻意的职责划分。

## 1.4 双后端：Docker 与 K8s，同一套接口

RCoder 通过 `ContainerRuntime` trait 把同一套应用语义映射到两套后端：

| 维度 | K8s（生产 / devspace 本地） | Docker（开发环境 / Compose） |
|---|---|---|
| 运行单元 | Deployment + Pod | 单容器 |
| 副本 | 真副本（replicas） | 单容器（replicas>0=存在，=0=stop） |
| env（非敏感） | ConfigMap | 容器 create 参数 |
| secrets（敏感） | Secret | 容器 create 参数 |
| 内部服务发现 | Service(ClusterIP) FQDN | 容器名（Docker network DNS） |
| HTTP 对外（默认 Pingora） | Pingora `/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}` → ClusterIP Service | Pingora `/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}` → container_ip |
| HTTP 对外（可选 gateway） | HTTPRoute `/apps/{app_id}`（仅 `http_expose=gateway`） | （无，Docker 始终走 Pingora） |
| TCP 对外 | 初期不对外（仅 ClusterIP） | 初期不对外（仅 Docker 网络内） |
| 持久存储 | 共享 PVC 的 `apps/{app_id}` subPath | bind-mount `app-workspace/{app_id}/` |

**关键**：这两套后端对外暴露的是**完全相同的 REST 契约**。你写一遍 Java 客户端，开发环境（Docker）和生产（K8s）都能用。后端是 RCoder 的内部实现细节，你不需要关心。

后端由部署时决定（K8s feature flag → KubernetesRuntime；否则 → DockerRuntime），运行时可通过环境变量 `RCODER_APP_ACCESS_MODE=docker|kubernetes` 覆盖。

## 1.5 职责分工表（务必对齐）

> 谁干什么，这是和 Java 同事对齐时最重要的一张表。

| 事项 | 谁负责 | 说明 |
|---|---|---|
| 应用元数据持久化（name/image/env/created_at/业务标签） | **Java** | RCoder 不存。读路径拿不到这些业务字段 |
| desired 状态的 source of truth | **Java** | RCoder 只在 create/update 时按你传的执行 |
| 把镜像跑起来、scale、restart、删计算资源 | **RCoder** | 转调后端 |
| 实时运行状态（status/replicas/pod_ip/端口） | **RCoder**（现场读集群） | 无缓存，每次查询都实时 |
| 持久数据（code/data/logs 目录） | **RCoder**（托管读写） + **Java**（决定何时清） | 删应用默认**保留**数据，由 Java 显式调 storage/clear 清理 |
| 外部访问 URL 的拼装 | **Java** | RCoder 只返回 path / 内部 FQDN / 端口号，见 §1.7 |
| 跨服务的对账（rcoder/Java 重启后） | **Java** 发起 | RCoder 提供 `GET /apps/runtime` 列全部托管应用，Java 对自己的 DB 做差异，见 [05-典型场景.md](./05-典型场景.md) |
| name / created_at 维度的过滤 | **Java** | RCoder 无状态，这些字段它没有；列表接口会忽略这类过滤条件（见 [02-接口手册.md](./02-接口手册.md)） |

## 1.6 资源命名与标签约定

RCoder 为每个应用生成的集群资源遵循统一命名和标签，方便你（或运维）在集群侧排查、对账。

- **app_id 格式**：`app-` + DNS-1123 label（如 `app-1a2b3c4d`、`app-order-svc`）。由 RCoder 在创建时自动生成（`Uuid::v4()` 前 8 位），或 create 时由调用方外部指定（可选 `app_id` 字段，校验 `app-` 前缀 + DNS-1123 + 唯一性，已存在 → `409 ERR_APP_ALREADY_EXISTS`）。**直接进入文件系统路径拼接，因此 RCoder 会严格校验格式**——非法 app_id（含 `..`、绝对路径等）返回 `400 ERR_VALIDATION`。固定 app_id 是「误删找回」的前提（见 [05 场景 4](./05-典型场景.md)）。
- **资源命名前缀**：`ServiceType::UserApp` 的前缀是 `rcoder-app`：
  - 计算单元：`rcoder-app-{app_id}`
  - 内部服务：`rcoder-app-{app_id}-svc`
  - K8s TCP 对外：`rcoder-app-{app_id}-nodeport`（**初期不建**，TCP 不对外）
  - HTTP 路由：`rcoder-app-{app_id}-route`（**仅 gateway 模式建**）
- **统一标签**（所有托管资源都打）：
  - `app.kubernetes.io/instance={app_id}`
  - `app.kubernetes.io/managed-by=rcoder-app-manager`
  - `app.kubernetes.io/name=user-app`
  - 多租户：`rcoder.io/tenant={tenant_id}`、`rcoder.io/space={space_id}`（create/update 时由请求体携带生成）

这套标签是 RCoder "无状态对账"的地基：RCoder 重启后，靠 `managed-by=rcoder-app-manager` 反查集群就能重建所有托管应用的 observed 视图。

## 1.7 服务暴露：URL 怎么拼

**统一原则：RCoder 一律只返回 path，host 由 Java 拼。**

客户端要通过 RCoder 才能访问应用，所以 Java 必然已持有 RCoder（或 gateway）的入口地址——否则请求根本进不来。RCoder 在 `access` 里只返回 path，host 留给 Java 拼上自己已知的入口。这避免 RCoder 依赖外部域名配置，也避免多环境（生产/预发/租户）域名耦合。

### HTTP 两种暴露模式（`http_expose` 配置切换）

| 模式 | RCoder 返回 path | Java 拼 host | 最终 URL |
|---|---|---|---|
| **Pingora（默认）** | `/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}` | RCoder 入口（Java 已知） | `{RCoder入口}/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}` |
| **Gateway（可选）** | `/apps/{app_id}` | gateway 域名（Java 已知） | `{gateway}/apps/{app_id}` |

- **Pingora 模式**（K8s / Docker 统一）：RCoder 内置 Pingora 反向代理，`/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}` 的流量转发到应用——K8s 转到 `{app_id}-svc:{port}`（ClusterIP Service），Docker 转到 container_ip。`access.external.http` 返回 `/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}`。
- **Gateway 模式**（仅 K8s 可选）：RCoder 创建 HTTPRoute 挂 `nuwax-gateway`，path `/apps/{app_id}`。Docker 无 gateway，始终走 Pingora。

> 两种模式**完全对称**：都是"RCoder 返 path + Java 拼 host"。默认 Pingora 是为了消除此前 K8s(gateway) / Docker(Pingora) 的分裂，让两后端 access 形态一致、Java 用一套拼接逻辑。

### TCP 端口（初期不对外）

TCP 服务（如容器内 PostgreSQL）**初期不支持对外**：`access.external.tcp` 留空；`access.internal` 返回 ClusterIP FQDN + 端口，供**同集群内**互调（如业务 Pod 连 app 的 PG）。

### access 结构

```jsonc
{
  "external": {
    "http": "/api/v1/userapp/proxy/app/prod/{user_id}/{app_id}",            // path（Pingora 默认）；gateway 模式为 "/apps/{app_id}"
    "tcp": []                            // 初期为空（TCP 不对外）
  },
  "internal": {
    "domain": "rcoder-app-{app_id}-svc.{ns}.svc.cluster.local",  // 集群内 FQDN
    "short_domain": "rcoder-app-{app_id}-svc.{ns}",
    "ports": [ { "name", "port" } ]      // 容器端口
  }
}
```

Java 拼装：`finalUrl = javaKnownHost + access.external.http`（Pingora 模式 host = RCoder 入口；gateway 模式 host = gateway 域名）。

> ⚠️ **已知限制（Pingora 内存态，两后端都有）**：Pingora backend 注册表（`pingora_ports`）是内存态，rcoder 重启后丢失。重启后**读路径**（get/query/runtime）的 `external.http` 会变 `null`（HTTP 端口信息补不回来，path 也返不出）；**create 响应不受影响**（用请求端口生成）。Java 应以 **create 响应**里的地址为准，或自行缓存。

## 1.8 持久存储目录约定

每个应用的持久存储（不论后端）都呈现为同一个三段目录结构，**路径契约一律以"app 根"为相对基准**：

```
{app 根}/                # K8s: PVC 的 apps/{app_id} subPath 挂到容器 /app
                         # Docker: app-workspace/{app_id}/
├── code/                # 应用代码（启动前上传，运行时通常只读）
├── data/                # 应用数据（读写）
└── logs/                # 应用文件日志（容器 stdout 之外的文件日志，读写）
```

| 后端 | app 根（RCoder 视角） | app 根（容器视角） |
|---|---|---|
| K8s | `/app/project_workspace/apps/{app_id}`（复用 rcoder-workspace PVC subPath） | `/app` |
| Docker | `{RCODER_WORKSPACE_ROOT}/{app_id}` | `/app`（bind-mount） |

文件管理接口（upload / files / files/delete）的 `path` / `target` 字段**一律 app 根相对**（如 `code/app.jar`），RCoder 内部做了 path traversal 防护（越界 → `400 ERR_VALIDATION`）。详见 [02-接口手册.md](./02-接口手册.md#文件管理)。
