# 12. 开发模式与文件接口（/api/userapp）

> 本篇覆盖 UserApp **开发阶段**：创建项目、编辑文件、AI 开发对话、跑命令、起 dev server，
> 直到交给 detect/confirm → build → publish 构建发布链。
> 接口入口 = **rcoder 主服务**（8086，`/api/userapp/*` + 经反向代理转发的 TS 老路径），
> 实际处理 = **该 app 的开发容器**（UserAppBuilder）内嵌 file-server（容器内 60000），
> rcoder 全量流式透传（multipart/SSE 均支持）。

## 1. 开发容器（核心概念）

**一个 app_id 一个独立开发容器**（镜像同 computer 沙箱 dev-rcoder-agent-runner，
容器独立），容器内起全套：agent_runner + 内嵌 file-server(60000) + PG。
开发数据落在该容器独占的 **per-app RWO 块卷**上（大量小文件编译 IO 不走 CephFS 元数据面）：

| 视角 | 路径/资源 | 说明 |
|---|---|---|
| 开发容器内 | `/home/user/userapp-workspace/`（整卷挂载） | `USERAPP_WORKSPACE_DIR` 镜像默认值；app workspace = `{根}/{app_id}` |
| K8s | per-app PVC `rcoder-app-builder-{app_id}-workspace`（**ReadWriteOnce**） | 运行时自动 ensure；storage class 缺省用集群 default（如 `ceph-rbd`，Ceph RBD 块存储；env `RCODER_USERAPP_BUILDER_STORAGE_CLASS` 可显式覆盖） |
| Docker Compose | 宿主 `./userapp-workspace/{app_id}` → 容器 `/home/user/userapp-workspace` | per-app bind（本地盘） |
| 与 UserApp 运行容器的关系 | 双容器并存（`ServiceType` 区分） | 开发新版时旧版继续服务（三阶段发布形态）；activate 才切流 |

要点：

- **开发/构建同容器**：build/dev server/文件操作都在开发容器内执行，无跨容器文件搬运；
  构建产物 `workspace-package-{release_id}.zip` 落 workspace，经
  `GET /api/userapp/static/{appId}/{file}` 下载流转（publish 链路同源）。
- **生命周期**：`POST /api/userapp/workspace`（创建项目显式入口）ensure 容器 + 建目录 +
  注册 owner；app 彻底删除（purge）时 rcoder 自动回收开发容器 + per-app PVC。
- **AI 开发对话**：`POST /computer/chat` body 可选字段 `service_type: "userapp"` +
  `project_id=app_id` → 路由到开发容器的 agent_runner，ACP agent 直接在开发卷 workspace
  工作（代码生成直接落卷）；不传 `service_type` = 原 computer 沙箱对话，零扰动。

## 2. 调用入口与反向代理分流

```
Java ──┬─ TS 老路径（/api/computer/*）+ X-Service-Type: userapp + X-App-Id
       │     → 反向代理(60000) → rcoder(8086) 同路径透传 → 目标容器（workspace 切 {开发卷}/{cId}）
       │
       └─ userApp 新接口（/api/userapp/*，带 X-App-Id header）
             → rcoder(8086) 通配转发 → 目标容器
```

- 经反代的 TS 老路径**参数原样**（`userId`+`cId`=app_id），multipart 零解析透传；
- 新接口 `appId` 定位；两类入口统一 `X-App-Id` header 定位目标容器（rcoder 零 body 解析）；
- 详细对接（header 约定/端口表/TS 可不改说明）见 **13 篇·反向代理对接指引**。

### 2.5 dev/prod 阶段分派（X-App-Stage header）

**目标容器**由可选 header `X-App-Stage` 决定（同一 app_id 可同时存在开发容器与
生产 Deployment，必须显式区分）：

| X-App-Stage | 目标 | 行为 |
|---|---|---|
| 缺省 / `dev` | 开发容器（UserAppBuilder） | 现状语义：注册表定位 + 探活自愈，miss 自动创建 |
| `prod` | 生产运行容器（UserApp） | **存在性检查（未知 app 404）→ 自动唤醒**（闲置回收 scale0 的 app 拉起，超时 503+Retry-After: 15）→ 转发其容器内 file-server-proxy :60000 |

- 生产运行容器内 file-server 为**单 app 模式**（卷根即 app 根；`appId` 必须与容器
  归属一致，跨 app 访问 400）；
- 未知值（非 dev/prod）→ 400 fail-fast（拼错 header 不该静默落错容器）；
- 生产容器的 workspace 即 RBD 运行卷根（`/app`，含 code/data/logs）——开发期
  文件族（upload-file/get-file-list 等）在生产容器同样可用，路径语义 app 根相对。

## 3. 文件操作接口（15 个，computer 域同参镜像）

参数风格 camelCase；`appId` ≡ app_id（定位 `{开发卷}/{appId}`）；`userId` 保留但**不参与
路径**（仅审计）；`customTargetDir` 非空时**直接信任**作为目标根（由 Java 侧负责合法性，
与 computer 域同语义）。响应为裸 `{success, message, …}`（不包 HttpResult）。

### 文件读（GET，Query 传参）

| 接口 | 功能 | 参数 |
|---|---|---|
| `/api/userapp/get-file-list` | 文件树列表（轻量元信息；`recursive=false` 单层） | appId、userId、proxyPath、customTargetDir、relativePath、recursive |
| `/api/userapp/resolve-file` | 文件存在性解析 + 预览 URL | appId、userId、proxyPath、customTargetDir、filePath |
| `/api/userapp/search-files` | 无索引有界搜索 | appId、userId、proxyPath、customTargetDir、relativePath、kw、limit、maxVisit、timeoutMs（均必填正整数） |

### 文件写（POST）

| 接口 | 传参 | 说明 |
|---|---|---|
| `/api/userapp/files-update` | Json：appId、userId、customTargetDir、files[] | 批量 create/delete/rename/modify（modify 字节比较） |
| `/api/userapp/upload-file` | Multipart：appId、userId、filePath、customTargetDir、file | 单文件上传 |
| `/api/userapp/upload-files` | Multipart：appId、userId、customTargetDir、filePaths*、files* | 多文件（单文件失败不影响其余，响应逐文件结果） |
| `/api/userapp/generate-file` | Json：appId、userId、fileName、content、customTargetDir | 文本生成文件（fileName 可含相对子路径） |
| `/api/userapp/import-project` | Multipart：appId、userId、customTargetDir、file(zip) | 项目 zip 导入（白名单合并） |

### 下载（二进制 zip 响应）

| 接口 | 传参 | 说明 |
|---|---|---|
| `/api/userapp/zip-workspace` | Json：appId、userId、excludeDirs | 打包下载（保留 .gitignore 等 dot 文件） |
| `/api/userapp/download-all-files` | Query：appId、userId、customTargetDir | 全量下载（顶层前缀 `{userId}_{appId}/`；超 100MB 报错） |

### 执行与环境

| 接口 | 传参 | 说明 |
|---|---|---|
| `/api/userapp/execute-command` | Json：appId、userId、command | 终端命令（cwd=workspace，shell -c，超时=DEV_COMMAND_TIMEOUT_SECS） |
| `/api/userapp/get-logs` | Query：appId、userId、tailLines(默认200) | 最近执行日志（`.logs/` 下 mtime 最新文件末尾 N 行） |
| `/api/userapp/install-project` | Json：appId、userId、programmingLanguage | 依赖安装：typescript/ts→pnpm；python/py→pip |

### 初始化

| 接口 | 传参 | 说明 |
|---|---|---|
| **`POST /api/userapp/workspace`** | Json：appId、userId | **创建项目显式入口**：ensure 开发容器 + 幂等建目录 + 注册 owner（幂等，重复调用安全） |
| `/api/userapp/init-project-template` | Multipart：appId、userId、file(zip)、enableGit | 模板 zip 解压到 `{开发卷}/{appId}/`（zip 内应含顶层项目目录）；enableGit=true 且 GIT_ENABLED 时自动 git init |
| `/api/userapp/push-skills-to-workspace` | Multipart：appId、userId、file(zip)、skillUrls(JSON数组)、agentId | 技能推到 `{ws}/.agents/skills` |

## 4. 与既有接口的衔接（全链同容器）

```
POST /api/userapp/workspace（ensure 容器）──┐
init-project-template / upload ────────────┼→ 开发容器 {开发卷}/{appId}/
/computer/chat + service_type=userapp ─────┘        │
                                                    → POST /api/userapp/projects/detect
                                                    → POST /api/userapp/projects/confirm
                                                    → POST /api/userapp/build（制品落同 workspace）
                                                    → GET  /api/userapp/static/{appId}/{file}
                                                    → rcoder POST /api/v1/apps/{appId}/publish
```

- `detect` / `confirm` / `build` / `static`（存量接口）与文件接口**同一容器同一棵卷**。
- **开发服务生命周期（appId 唯一 key）**：

| 接口 | 传参 | 说明 |
|---|---|---|
| `POST /api/userapp/dev/start` | Json：appId、userId、basePath? | **异步任务：manifest 同核编译 → 成功后启动**（编译数分钟，立即返 taskId）。已在跑时快速完成不编译（上新代码用 restart）；编译失败不启动 |
| `POST /api/userapp/dev/stop` | Json：appId、userId | 同步停止（按 appId 定位进程组，无需 pid）；**联动取消该 app 在途的 start/restart 任务** |
| `POST /api/userapp/dev/restart` | Json：appId、userId、basePath? | **异步任务：manifest 同核编译 → 成功后 stop+start**（重启前必先编译，新代码才生效）；编译失败旧服务保留 |
| `GET /api/userapp/dev/list` | — | 在跑的 UserApp 开发服务列表（**start/restart 终态后端口从这里查**，manifest 项目恒 9080） |
| `GET /api/userapp/dev/logs` | Query：appId、startIndex?、logType?(main/temp) | 开发服务日志 |

- **异步任务消费方式**（start/restart）：响应 `{taskId, status:"pending"}`；轮询
  `GET /api/userapp/tasks/{taskId}`（终态含错误信息）、SSE
  `GET /api/userapp/tasks/{taskId}/logs/stream`、取消 `POST /api/userapp/tasks/{taskId}/cancel`。
- 编译与生产构建 `/api/userapp/build` 同核（dev 编译通过 = 可部署）；纯编译不启动用
  `/api/userapp/build`。basePath 对 manifest 项目无效（pingap 路由前缀由
  project.manifest.toml `[proxy].path` 决定）。

## 开发预览代理（与部署访问统一形态，免端口）

```
开发中:  {Pingora入口}/proxy/userapp/dev/{user_id}/{app_id}/{path}   → 该 app 开发容器 pingap(9080)
部署后:  {Pingora入口}/proxy/userapp/prod/{user_id}/{app_id}/{path}  → app 运行容器 pingap(9080)
```

- **免端口**：代理内部固定拨 pingap 统一入口 9080（manifest 流程 `POST /api/userapp/dev/start`
  恒起 app-cli+pingap，`GET /api/userapp/dev/list` 的 `port` 恒为 9080 仅作展示，
  start/restart 已改异步任务不再同步返回 port）。
- **零注册零状态**：Java 用 `user_id` + `app_id` 二元组直接拼 URL（Pingora 入口即 rcoder 的
  8088 端口）；upstream 按 `app_id` 动态解析该 app 开发容器。
- `user_id` 不参与解析（per-app 容器），用于日志排障与未来归属鉴权。
- 多 app 并行：每 app 独立开发容器，app-a/app-b 各拼各的 URL。
- 部署后 `access.external.http` 返回 `/proxy/userapp/prod/{user_id}/{app_id}`（owner `user_id` 落 `userapp_metadata`）——
  **开发切部署前端只改 `dev`→`prod` 一段**。
- 局限：开发容器重建后 IP 变化有短窗口旧值（下次 ensure 修正）；无开发容器 → 502。

## 4.5 开发终端/桌面/语音/输入法（Pingora 代理，按 app_id）

```
Web 终端:  /userapp/dev/ttyd/{app_id}/{path}   （cwd=开发卷/{app_id}，ws 子协议 tty）
远程桌面:  /userapp/dev/vnc/{app_id}/{path}    （noVNC 页面 + websockify WS）
语音:      /userapp/dev/audio/{app_id}/{path}  （ws→6089 流 / 其余→6090）
输入法:    /userapp/dev/ime/{app_id}/{path}    （6091 WebSocket connect）
```

前置 `POST /api/userapp/workspace`（开发容器未注册 404）；Pingora 入口 8088 / NodePort 30435。
开发容器是完整桌面镜像（Xvnc+noVNC+ttyd+IME+音频全套），AI 对话生成的代码与终端手工操作
落同一开发卷。对接细节见 13 篇 §5.5。

## 5. PG 凭据对齐（dev/prod 双环境）

开发与部署容器内 PG 账号密码保持一致（Java 持有目标凭据，调用对齐接口）：

```
POST /api/userapp/db/dev/align-credentials    → 开发容器内 PG
POST /api/userapp/db/prod/align-credentials   → 运行容器内 PG
body: { app_id, username, password }（snake_case）
```

流程：TCP scram 验证传入密码 → 一致直接返回（`reset_performed=false`）；不一致先查角色
存在（缺号明确报错）→ trust `ALTER USER` 重置 → 复验。密码不落日志。

## 6. Java 对接指引（从 computer 域迁移）

两条路线任选（也可混用）：

1. **走反向代理**（复用既有 TS 调用代码）：URL 不变，加 `X-Service-Type: userapp` +
   `X-App-Id` 两个 header（见 13 篇）；
2. **直连新接口**：URL 前缀 `/api/computer/*` → `/api/userapp/*`，参数 `cId` → `appId`
   （其余同构；响应回显键同步 `cId`→`appId`）。

不迁移的 computer 接口：`create-workspace(-v2)`/`delete-workspace`（workspace 生命周期归
rcoder 编排，用 `POST /api/userapp/workspace` 替代）、`build-agent-package`/
`cleanup-build-artifacts`（nuwax agent 包链路）。

## 7. 部署注意

- K8s：开发容器 per-app RWO PVC 运行时自动 ensure（无需 helm 预建）；本地 devspace 需
  `RCODER_USERAPP_BUILDER_STORAGE_CLASS=local-path`（已配置在 k8s/config/deployment.yaml）。
- Docker Compose：宿主 `./userapp-workspace/{app_id}` per-app bind（rcoder 容器挂
  `/app/userapp-workspace` 作反解锚点）；目录由 starter 自动预建。
- 存量升级：旧共享卷方案（RWX + 沙箱二挂）已废弃；升级前如曾部署共享卷版本，删除
  存量 builder STS 与共享 PVC（数据迁移按需导出导入）。
