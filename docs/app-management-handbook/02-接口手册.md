## 2.1 通用约定

| 约定 | 内容 |
|---|---|
| **URL 前缀** | 所有接口统一 `/api/v1` |
| **HTTP 方法** | **只允许 `GET`（读）与 `POST`（写）**，禁用 DELETE/PUT/PATCH。写操作的动词直接放进 path（`/delete`、`/update`、`/files/delete`、`/storage/delete`）。这是部署环境网关的硬性限制 |
| **响应包装** | 所有响应统一包 `HttpResult<T>`（见下）；错误也走同一结构 |
| **app_id** | 路径参数 `{app_id}`，格式 `app-` + DNS-1123 label（如 `app-1a2b3c4d`、`app-order-svc`）。可由 RCoder 自动生成或 create 时外部指定（可选 `app_id` 字段）。**进入文件路径拼接，严格校验**，非法格式 `400 ERR_VALIDATION` |
| **时间字段** | 所有时间均为 RFC3339 字符串（如 `created_at`、`modified_at`、`started_at`） |
| **缺省值** | `tail` 类参数未传时取默认值（日志快照 1000、文件日志 100、WS 流 0）；分页默认 page=1 / page_size=20 |

### HttpResult 统一响应体

```jsonc
{
  "success": true,            // 是否成功
  "data": { /* T 或 null */ }, // 成功时的业务数据
  "code": "SUCCESS",          // 业务码（成功 SUCCESS，失败 ERR_*）
  "message": "操作成功",       // 人读信息
  "tid": "abc-123"            // 追踪 ID（可用于日志关联）
}
```

> 错误响应 `success=false`、`data=null`、`code=ERR_*`、`message` 为具体错误信息、HTTP 状态码与 code 对应。错误码与重试策略见 [03-错误处理与重试.md](./03-错误处理与重试.md)。

### 示例约定

下文 curl 示例中 `$RCODER` 指 RCoder 基地址：

```bash
# K8s（devspace 本地，端口 8290）
export RCODER=http://127.0.0.1:8290
# 或 Docker Compose（端口 8090）
export RCODER=http://127.0.0.1:8090
```

## 生命周期

### POST `/apps` — 创建应用

把一个镜像连同启动参数部署成可访问的长期运行服务。**异步语义**：RCoder 创建完资源立即返回（status 通常为 `Starting`），**不等 Pod Ready**——你需轮询 `GET /apps/{id}` 观察状态变迁。

**请求体** `CreateAppRequest`：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | ✅ | 应用名称（业务字段，仅记录于返回值，不影响资源命名） |
| `image` | string | ✅ | 容器镜像引用；当前阶段允许 `latest`（无 tag 时集群默认补 `:latest`） |
| `command` | string[] | ❌ | 启动命令（覆盖镜像 CMD；空数组等同于不传） |
| `env` | map<string,string> | ❌ | 环境变量（非敏感，K8s 存 ConfigMap） |
| `secrets` | map<string,string> | ❌ | 敏感信息（K8s 存 Secret） |
| `resources` | object | ❌ | 资源限制，见下 |
| `ports` | object[] | ❌ | 端口配置，见下 |
| `health_check` | object | ❌ | 健康检查配置，见下 |
| `tenant_id` | string | ❌ | 租户 ID（打 label `rcoder.io/tenant`） |
| `space_id` | string | ❌ | 空间 ID（打 label `rcoder.io/space`） |

`resources`（`ResourceLimits`）：

| 字段 | 示例 | 说明 |
|---|---|---|
| `cpu` | `"1"` / `"500m"` / `"0.5"` | CPU |
| `memory` | `"512Mi"` / `"1Gi"` | 内存 |
| `storage` | `"10Gi"` | 存储（K8s Quantity 格式，会校验） |
| `ephemeral_storage` | `"1Gi"` | 临时存储（overlay 可写层）；未设时回退 `storage` |

`ports[]`（`PortConfig`）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | ✅ | 端口名，如 `"http"` / `"postgres"` |
| `port` | u16 | ✅ | 容器端口 |
| `expose_type` | `"Http"` / `"Tcp"` | ✅ | 协议标识：Http 走 Pingora（默认）/ gateway（可选，挂 nuwax-gateway）；Tcp 初期不对外，仅集群内访问 |
| `strip_prefix` | bool | ❌ | **仅 gateway 模式 HTTP**。是否让网关剥掉 `/apps/{app_id}` 前缀；默认 `true`（后端收到 `/api`）；`false` 则保留完整路径由应用自行处理。Pingora 模式无此参数 |

`health_check`（`HealthCheckConfig`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `check_type` | `"Http"` / `"Tcp"` / `"Exec"` / `"None"` | 检查类型 |
| `path` | string? | HTTP 检查路径（check_type=Http 时用） |
| `port` | u16? | 检查端口 |

> ⚠️ `Exec` 健康检查**当前不支持**（运行时缺少 command 字段），传 `Exec` 会返回 `400 ERR_VALIDATION`。请用 `Http` / `Tcp`。

**响应** `HttpResult<AppInfo>`：创建时返回完整 desired + 初始 observed 快照（`status`、`access`、`health`）。

```bash
curl -X POST "$RCODER/api/v1/apps" \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "my-java-app",
    "image": "registry.example.com/myapp:latest",
    "command": ["java", "-jar", "/app/code/app.jar"],
    "env": { "SPRING_PROFILES_ACTIVE": "prod" },
    "secrets": { "DB_PASSWORD": "s3cr3t" },
    "resources": { "cpu": "1", "memory": "1Gi", "ephemeral_storage": "2Gi" },
    "ports": [
      { "name": "http", "port": 8080, "expose_type": "Http" },
      { "name": "debug", "port": 5005, "expose_type": "Tcp" }
    ],
    "health_check": { "check_type": "Http", "path": "/actuator/health", "port": 8080 },
    "tenant_id": "tenant-a",
    "space_id": "space-1"
  }'
```

**要点**：
- `app_id` 由 RCoder 自动生成（`app-xxxxxxxx`），或 create 时外部指定（可选 `app_id` 字段，如 `app-order-svc`；校验 `app-` + DNS-1123 + 唯一性，已存在→`409 ERR_APP_ALREADY_EXISTS`）。在响应的 `app_id` 字段返回，后续所有操作用它。
- 创建是异步的，别假设返回时已 Ready。轮询 `GET /apps/{id}`，`status` 从 `Starting` → `Running`。
- `storage` / `ephemeral_storage` 必须是合法 K8s Quantity，否则 `400 ERR_VALIDATION`。
- 若同名资源已存在，返回 `409 ERR_APP_ALREADY_EXISTS`。

### POST `/apps/query` — 查询应用列表

实时查集群后做过滤/分页。**用 body 承载过滤条件**（规避 URL 编码/长度限制）。

**请求体** `QueryAppsRequest`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `page` | u32? | 页码，默认 1 |
| `page_size` | u32? | 每页数量，默认 20，上限 100 |
| `filters` | object? | 过滤条件，见下 |
| `sort_by` | string? | 排序字段，仅 `app_id` / `name` 生效 |
| `sort_order` | `"Asc"` / `"Desc"`? | 默认升序 |

`filters`（`AppFilters`）：

| 字段 | 是否生效 | 说明 |
|---|---|---|
| `status` | ✅ 生效 | 按状态过滤，`AppStatus[]` |
| `app_ids` | ✅ 生效 | 按 app_id 精确过滤 |
| `name` | ❌ **忽略** | 需业务元数据，RCoder 无状态无此字段（会 warn） |
| `created_at` | ❌ **忽略** | 同上 |

> 🔧 **name / created_at 维度的过滤请 Java 自己做**（RCoder 列表 + 你本地 DB 元数据二次过滤）。

**响应** `HttpResult<PaginatedResponse<AppRuntimeInfo>>`，其中 `pagination` 含 `page / page_size / total / total_pages`。

```bash
curl -X POST "$RCODER/api/v1/apps/query" \
  -H 'Content-Type: application/json' \
  -d '{
    "page": 1,
    "page_size": 20,
    "filters": { "status": ["Running", "Starting"], "app_ids": ["app-1a2b3c4d"] },
    "sort_by": "app_id",
    "sort_order": "Asc"
  }'
```

### GET `/apps/runtime` — 对账：列出全部托管应用

无状态引擎的关键接口。列出集群中**所有** `managed-by=rcoder-app-manager` 的应用运行时状态。供 Java 在 RCoder 或自身重启后对账。

**响应** `HttpResult<Vec<AppRuntimeInfo>>`（无分页，全量返回当前所有托管应用）。

```bash
curl "$RCODER/api/v1/apps/runtime"
```

**要点**：这是"应用侧"对账入口，与 [持久存储管理](#post-appsstoragequery--分页查询持久存储) 的"数据侧"对账互补。典型用法见 [05-典型场景.md](./05-典型场景.md#场景-rcoder--java-重启后对账)。

---

### GET `/apps/{app_id}` — 获取运行时详情

实时查集群，返回 observed 状态。

**响应** `HttpResult<AppRuntimeInfo>`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `app_id` | string | 应用 ID |
| `status` | enum | headline 状态（见下表），由 phase 映射 |
| `phase` | string | 运行时原始 phase：`Running` / `Stopped` / `Starting` / `Error` 等 |
| `message` | string? | phase=Error 时的失败原因（如 `CrashLoopBackOff`、容器退出码） |
| `replicas` | i32 | 期望副本数 |
| `ready_replicas` | i32 | 就绪副本数 |
| `restart_count` | u32 | 重启次数 |
| `pod_ip` | string? | Pod IP（K8s）/ 容器 IP（Docker） |
| `node` | string? | 所在节点（仅 K8s） |
| `started_at` | string? | 启动时间（RFC3339） |
| `ports` | object[] | 端口运行时状态；Pingora 模式 external_port 通常 None（HTTP 经 Pingora，TCP 不对外） |
| `access` | object | 访问信息（见 [01-定位与核心概念 §1.7](./01-定位与核心概念.md#17-服务暴露url-怎么拼)） |
| `conditions` | object[] | 诊断条件（read 时派生，见下） |

`status`（`AppStatus`）枚举与 phase 映射：

| 集群观测 | `status` | 说明 |
|---|---|---|
| replicas=0 | `Stopped` | 已 scale 到 0 |
| replicas>0 且 ready=0 | `Starting` | 启动中 |
| replicas>0 且 ready≥1 | `Running` | 运行中 |
| CrashLoopBackOff / ImagePullBackOff / 退出码≠0 | `Error` | 失败 |
| Deployment 不存在 | （404 `ERR_APP_NOT_FOUND`） | 应用不存在 |

`conditions[]`（`Condition`）：K8s conditions 风格，**read 时由 DeploymentStatus 派生**，用于细粒度诊断（如区分 `CrashLoopBackOff` vs `ImagePullBackOff`）。字段：`type`(Ready/Available/Progressing/Error)、`status`(True/False/Unknown)、`reason`、`message`、`last_transition_time`（无状态下通常为 null）。

> **status vs conditions**：`status` 给 Java 做状态机判断（粗粒度、稳定）；`conditions[]` 给人/前端做诊断（细粒度、含 reason）。二者同源派生、不矛盾。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d"
```

**要点**：
- 精确区分两种"查不到"：集群中真不存在 → `404 ERR_APP_NOT_FOUND`；API Server 不可达/RBAC 拒绝 → `500 ERR_BACKEND_ERROR`。**不要把瞬时 500 当成"应用不存在"去重建**，否则会误删在用资源。

### POST `/apps/{app_id}/update` — 更新应用

**全量替换 desired state**。RCoder 无状态，不持有旧 desired，所以无法做"部分字段保留"——**你需发送完整新状态，`image` 必填**。K8s 走 SSA re-apply（幂等），Docker 重建容器；工作空间目录保留。

**请求体** `UpdateAppRequest`（字段同 CreateAppRequest，但全部 Option，`image` 必填；`name` 仅元数据，RCoder 忽略）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `image` | ✅ | **必填**（RCoder 无状态无法保留旧 image；缺失 → `400 ERR_VALIDATION`） |
| `command` / `env` / `secrets` / `resources` / `ports` / `health_check` | ❌ | 整段替换语义（`ports` / `health_check` 是整段替换，由 SSA + orphan 扫描保证） |
| `tenant_id` / `space_id` | ❌ | 携带以保持资源 label（RCoder 不主动改租户归属） |
| `name` | ❌ | 仅元数据，RCoder 忽略 |

**响应** `HttpResult<AppRuntimeInfo>`（更新后的 observed 状态）。

```bash
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/update" \
  -H 'Content-Type: application/json' \
  -d '{
    "image": "registry.example.com/myapp:v2",
    "command": ["java", "-jar", "/app/code/app.jar"],
    "env": { "SPRING_PROFILES_ACTIVE": "prod" },
    "resources": { "cpu": "2", "memory": "2Gi" },
    "ports": [ { "name": "http", "port": 8080, "expose_type": "Http" } ],
    "health_check": { "check_type": "Http", "path": "/actuator/health", "port": 8080 }
  }'
```

**要点**：
- 这是**全量替换**：想改 `env` 就把完整 env 传全；想改 `image` 也得把 ports/env 等一并带上。
- 幂等：同一请求重复发，结果一致（K8s SSA 保证）。
- 应用不存在 → `404 ERR_APP_NOT_FOUND`。
- `Exec` 健康检查同样不支持（`400 ERR_VALIDATION`）。

### POST `/apps/{app_id}/delete` — 删除应用

**默认只删计算面（Deployment/Service/路由/配置），保留持久数据**（code/data/logs 目录）。需要连数据一起清，传 `purge: true`。

**请求体** `DeleteAppRequest`（可省略 body）：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `purge` | bool? | `false` | `true` 时同时清空持久存储（等价于删完再调 `storage/delete`） |

**响应** `HttpResult<String>`（"删除成功"）。

```bash
# 默认：保留数据
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/delete"

# 一键连数据清空
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/delete" \
  -H 'Content-Type: application/json' -d '{ "purge": true }'
```

**要点**：
- **默认保留数据**是刻意的安全设计：应用可重建，数据不可再生。误删应用若连带抹掉 data/ 是灾难。
- 删完计算资源后，持久目录仍在；用同一 app_id 重新 create 会自动挂回旧数据（适合"误删找回"）。
- 想要干净起点：先 delete（保留数据）→ 确认无误 → 调 `storage/delete` 清数据；或直接 `purge=true`。

## 操作

三个操作都转调后端 Deployment 能力，**先校验应用存在**（不存在 → `404 ERR_APP_NOT_FOUND`，便于 Java 触发 create 重建，而非当成系统故障）。返回更新后的 `AppRuntimeInfo`。

| 方法 | 路径 | 动作 |
|---|---|---|
| `POST` | `/apps/{app_id}/start` | scale replicas = 1 |
| `POST` | `/apps/{app_id}/stop` | scale replicas = 0（停止不删，数据/配置保留） |
| `POST` | `/apps/{app_id}/restart` | rollout restart（触发重建） |

```bash
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/start"
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/stop"
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/restart"
```

> **stop vs delete**：stop 是 scale=0（资源还在，重启快、配置不变）；delete 是拆资源（计算面没了，但数据默认保留）。

## 查询

### GET `/apps/{app_id}/logs` — 日志快照

拉取容器 stdout/stderr 的历史日志快照。

**Query 参数** `LogParams`：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `tail` | u32? | `1000` | 返回最后 N 行 |
| `follow` | bool? | — | **当前未实现**（runtime 仍返回快照）；实时流用 `logs/stream` |
| `timestamps` | bool? | `true` | 是否带时间戳 |
| `since` | string? | — | **暂未透传**（保留字段） |

**响应** `HttpResult<Vec<LogEntry>>`，`LogEntry = { timestamp, stream("stdout"/"stderr"), message }`。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/logs?tail=200&timestamps=true"
```

---

### GET `/apps/{app_id}/logs/file` — 文件日志

从工作空间 PVC 的 `logs/` 目录**直接读文件**，不依赖容器 log API。适用**不写 stdout 而写文件**的应用（如 Java Spring Boot 的 `logs/application.log`）。

**Query 参数** `FileLogQuery`：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `path` | string | — | **必填**。日志文件路径，app 根相对（如 `logs/application.log`） |
| `tail` | u32? | `100` | 返回最后 N 行 |

**响应** `HttpResult<Vec<LogEntry>>`（`stream` 字段为 `"file"`，`timestamp` 通常为空——文件日志不带时间戳）。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/logs/file?path=logs/application.log&tail=200"
```

**要点**：有 path traversal 防护，越界 → `400`；文件不存在 → `404 ERR_FILE_NOT_FOUND`。

---

### GET `/apps/{app_id}/logs/stream` — 日志 WebSocket 流

实时 follow 日志。**WebSocket upgrade**，服务端逐行推送 `LogEntry` JSON。

**Query 参数** `LogStreamQuery`：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `tail` | u32? | `0` | 起始历史行数；`0` = 仅 follow 新行 |

**协议**：
- 服务端 → 客户端：每条日志一个 `Text` 帧，内容为 `LogEntry` 的 JSON。
- 客户端断开连接 → 服务端停止 follow（receiver 析构 → 后台任务终止）。

```bash
# wscat 示例
wscat -c "$RCODER_WS/api/v1/apps/app-1a2b3c4d/logs/stream?tail=100"
```

> 为什么 WebSocket 不是 SSE：双向（Java 可发控制帧/主动停）、与 K8s/Docker 自身日志流一致、可切换 tail。详见 [04-设计考虑.md](./04-设计考虑.md#为什么日志流用-websocket-而非-sse)。

### GET `/apps/{app_id}/health` — 健康状态

由运行时状态派生（`AppRuntimeInfo` → `HealthInfo`）。

**响应** `HttpResult<HealthInfo>`：`{ status, instance: {name, phase, ready, restart_count, node, ip, started_at}, probes: null }`。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/health"
```

---

### GET `/apps/{app_id}/stats` — 资源使用

**best-effort**。当前实现只可靠返回 `restart_count`；CPU/内存需集群装 metrics-server（K8s）或 Docker 原生统计，**当前返回默认空值**（`0`），后续增强。

**响应** `HttpResult<ResourceStats>`：`{ cpu: {usage_percent, usage_cores, limit_cores}, memory: {usage_bytes, usage_percent, limit_bytes}, network: {rx_bytes, tx_bytes}, restart_count }`。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/stats"
```

### GET `/apps/{app_id}/events` — 应用事件

K8s Events（调度/拉取/启动/崩溃）转调后端。Docker 后端能力有限。

**响应** `HttpResult<Vec<AppEventInfo>>`。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/events"
```

## 文件管理

> 路径契约：`target` / `path` 字段**一律 app 根相对**（如 `code/app.jar`、`data/db/`），不带前缀默认指向 app 根。有 path traversal 防护，越界 → `400 ERR_VALIDATION`。

### POST `/apps/{app_id}/upload` — 上传文件 / 压缩包（自动判断）

**multipart/form-data**，字段：
- `file`（文件/压缩包，必填）
- `target`（app 根相对；默认 `code/{原文件名}`）
- `flatten`（可选，`true`/`false`，默认 `false`；压缩包是否剥单层 wrapper 目录）

**自动判断（魔数）**：
- **zip / tar.gz** → 解压到 `target` 目录（`target` 是目录，如 `code/`），保留压缩包内目录结构。
- **其它**（单文件，如 jar/二进制）→ 存为 `target`（文件路径，如 `code/app.jar`）。

**响应** `HttpResult<UploadResult>`：`{ file_path, file_size, uploaded_at, extracted_count? }`。
- `extracted_count`：压缩包解压的文件数（单文件为 `null`/省略）。

**安全**：zip slip 防护（拒绝 `../` 路径穿越）+ 解压总大小 ≤ 1GiB（超限 `400 ERR_VALIDATION`）；均复用 `download_utils`。

```bash
# 单文件（app.jar）
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/upload" \
  -F "file=@./app.jar" -F "target=code/app.jar"

# 压缩包（前端 dist.zip → 解压到 code/，保留目录结构）
zip -r dist.zip dist/
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/upload" \
  -F "file=@./dist.zip" -F "target=code/"
# → extracted_count=N，code/index.html、code/css/、code/assets/ 等解压出来

# tar.gz + flatten（剥 wrapper 目录）
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/upload" \
  -F "file=@./app.tar.gz" -F "target=code/" -F "flatten=true"
```

---

### GET `/apps/{app_id}/files` — 列出文件

**Query**：`path`（可选，子目录 app 根相对，如 `code` / `data` / `logs`；默认列 app 根）。

**响应** `HttpResult<Vec<FileInfo>>`：`{ path, size, is_dir, modified_at }`。返回的 `path` 字段是 **app-root-relative**（如 `code/app.jar`），可直接作为 upload 的 target / delete 的 path。

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/files?path=code"
curl "$RCODER/api/v1/apps/app-1a2b3c4d/files"
```

---

### POST `/apps/{app_id}/files/delete` — 删除文件

**请求体** `DeleteFileRequest`：`{ "path": "code/app.jar" }`（app 根相对，可指向 code/data/logs 下任意文件或目录）。

**响应** `HttpResult<String>`（"文件删除成功"）。

```bash
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/files/delete" \
  -H 'Content-Type: application/json' -d '{ "path": "code/app.jar" }'
```

**要点**：文件/目录不存在 → `404 ERR_FILE_NOT_FOUND`；应用目录不存在 → `404 ERR_APP_NOT_FOUND`。

## 持久存储管理

> 删应用默认保留数据；这组接口让你显式查询/清空"残留数据"。`StorageInfo` **不含 `size_bytes`**——CephFS 上不能用 `du`，详见 [04-设计考虑.md](./04-设计考虑.md#为什么存储信息不含-size_bytes)。

### GET `/apps/{app_id}/storage` — 查询存储状态

**O(1) 单次 stat**（不递归遍历）。

**响应** `HttpResult<StorageInfo>`：`{ app_id, exists, path, modified_at?, is_orphan }`。

| 字段 | 说明 |
|---|---|
| `exists` | 目录是否存在 |
| `path` | app 根路径（RCoder 视角） |
| `modified_at` | 最近修改时间（RFC3339） |
| `is_orphan` | 是否孤儿（无对应运行应用）—— 实时查集群判定 |

```bash
curl "$RCODER/api/v1/apps/app-1a2b3c4d/storage"
```

---

### POST `/apps/{app_id}/storage/delete` — 清空持久存储

**安全约束**：仅当该 app 的计算资源已不存在（即已 delete）时才允许；若 app 仍存在，返回 `409 ERR_INVALID_STATE`。

强制工作流：`delete app（数据保留）→ 确认无误 → storage/delete`。

```bash
curl -X POST "$RCODER/api/v1/apps/app-1a2b3c4d/storage/delete"
```

**要点**：实现上是删共享 PVC 上的 `apps/{app_id}` 目录（K8s，不删 PVC 本身）或 `app-workspace/{app_id}/` 目录（Docker）。

---

### POST `/apps/storage/query` — 分页查询持久存储

**强制分页，无全量模式**（扫存储后端代价高）。

**请求体** `QueryStorageRequest`：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `page` | u32 | ✅ | 页码，**从 1 开始**（传 0 → `400`） |
| `page_size` | u32 | ✅ | **1..=100**（超范围 → `400`） |
| `filters` | object? | ❌ | 见下 |

`filters`（`StorageFilters`）：

| 字段 | 是否生效 | 说明 |
|---|---|---|
| `orphan_only` | ✅ | `true` = 只返回"有数据、无对应运行应用"的孤儿 |
| `app_ids` | ✅ | 按 app_id 精确过滤（最省扫描） |
| `tenant_id` / `space_id` | ❌ **忽略** | 无状态下 RCoder 不持 app→租户映射（会 warn） |

**响应** `HttpResult<PaginatedResponse<StorageInfo>>`。`is_orphan` 字段始终返回（无论是否过滤），便于识别孤儿。

```bash
curl -X POST "$RCODER/api/v1/apps/storage/query" \
  -H 'Content-Type: application/json' \
  -d '{ "page": 1, "page_size": 20, "filters": { "orphan_only": true } }'
```

**要点**：只单层列工作空间目录（不递归），每个条目 O(1) stat，规模可控。

## 应用访问入口（Pingora 代理）

部署的应用通过 RCoder 内置 Pingora 代理访问。`access.external.http`（如 `/proxy/apps/app-order-svc/8080`）即访问入口。

### GET `/proxy/apps/{app_id}/{port}/{path}` — 访问部署的应用

**不是 RCoder 管理 API**——这是 Pingora 代理路径（直接打 Pingora 端口 8088），经 RCoder 内置代理转发到应用后端。按 `(app_id, port)` 路由（多 app 同端口不冲突）。

**路径**：`{Pingora入口}/proxy/apps/{app_id}/{port}/{path}`

| 参数 | 说明 |
|---|---|
| `{app_id}` | 应用 ID（如 `app-order-svc`） |
| `{port}` | 应用的 HTTP 端口（如 8080） |
| `{path}` | 应用内的路径（如 `/api/users`） |

```bash
# 访问 app-order-svc 的 HTTP 端口 8080 的 /api/users
curl http://{Pingora入口}:8088/proxy/apps/app-order-svc/8080/api/users
# → Pingora 转发到 app-order-svc 后端 :8080/api/users
```

**要点**：
- host（Pingora 入口）由 Java 拼（Java 已知 RCoder 入口）。
- 按 `(app_id, port)` 路由，未注册 → 502（Fail Fast，无兜底）。
- swagger 也有对应 axum 重定向接口（tag「应用管理」），但生产建议直接打 Pingora 端口。
- 与通用 `/proxy/{port}`（VNC 等）物理分离——app 专用 `/proxy/apps/`。

## 字段速查：AppStatus 枚举

```rust
pub enum AppStatus { Created, Starting, Running, Stopping, Stopped, Error, Deleting }
```

| 值 | 含义 |
|---|---|
| `Created` | 已定义（实际较少直接出现，多为 phase 未知时的兜底映射） |
| `Starting` | 启动中（replicas>0 且未 ready） |
| `Running` | 运行中（ready≥1） |
| `Stopped` | 已 scale 到 0 |
| `Stopping` | 停止中（派生场景） |
| `Error` | 失败（CrashLoopBackOff / ImagePullBackOff / 退出码≠0） |
| `Deleting` | 删除中 |

> 派生细节见 [04-设计考虑.md](./04-设计考虑.md#状态机) 的状态机图。
