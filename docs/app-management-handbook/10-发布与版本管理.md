# 10. 发布与版本管理

> UserApp 构建发布全流程：从源码构建镜像 → 上传制品 → 发布激活 → 版本回滚。这是**新增的发布体系**，与直接 create 部署并存。

---

## 发布体系概览

```
┌─────────────────────────────────────────────────────────────────┐
│  发布全流程（Java 业务侧视角）                                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 构建阶段                                                     │
│     POST /apps/{id}/build                                        │
│     └→ RCoder 在 builder 容器内编译源码 → 产出制品 zip           │
│         （异步：返回 task_id，轮询 GET /apps/publish/tasks/{id}）│
│                                                                 │
│  2. 预备阶段                                                     │
│     POST /apps/{id}/releases/prepare                             │
│     └→ RCoder 从 URL 下载制品包 + sha256 校验 → 入库（不切流）   │
│         （同步：校验通过即返回 ReleaseInfo）                      │
│                                                                 │
│  3. 激活阶段                                                     │
│     POST /apps/{id}/releases/{rid}/activate                     │
│     └→ 切换 code 软链 + 重启应用 → status=PendingStart          │
│         （同步：切流完成即返回，应用开始启动）                    │
│                                                                 │
│  4. 确认阶段                                                     │
│     POST /apps/{id}/releases/{rid}/confirm                      │
│     ├→ healthy=true  → 提交（转 Active）                        │
│     └→ healthy=false → 回滚到上一 Active 版本 + 置 Failed       │
│                                                                 │
│  5. （可选）中止                                                 │
│     POST /apps/{id}/releases/{rid}/abort                        │
│     └→ confirm 自身失败导致 pending 残留时的运维自救             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

---

## 发布状态机

```
Prepared ──activate──→ PendingStart ──confirm(healthy=true)──→ Active
                          │
                          └──confirm(healthy=false)──→ Failed（自动回滚到上一 Active）

幂等规则：
- 重复 activate 已 Active 的 release → 直接返回（幂等）
- 重复 confirm 已终态且结论一致 → 直接返回
- confirm 非待确认状态 → 409 ERR_INVALID_STATE
```

## 构建接口

### POST `/apps/{app_id}/build` — 触发源码构建

在 UserApp Builder 容器内编译源码（自动 ensure builder），产出可部署制品 zip。

**请求体** `BuildBody`：
```jsonc
{
  "project_id": "app-order-svc"  // 源码所在 project（与 app_id 关联的构建项目）
}
```

**响应** `HttpResult<PublishTaskData>`：
```jsonc
{
  "success": true,
  "data": {
    "task": {
      "id": "019123456789abcdef",
      "app_id": "app-order-svc",
      "kind": "build",
      "status": "running",
      "stage": "preparing",
      "created_at": "2026-08-15T10:00:00Z"
    }
  }
}
```

**错误**：
| HTTP | code | 说明 |
|---|---|---|
| 400 | ERR_VALIDATION | 参数错误（app_id/project_id 不合法） |
| 404 | ERR_NOT_FOUND | Agent-runner 或 builder 容器不可达 |
| 409 | ERR_CONFLICT | 同 app 已有活跃构建/发布任务 |
| 429 | ERR_TOO_MANY_REQUESTS | 全局任务容量上限 |
| 500 | ERR_INTERNAL_SERVER_ERROR | 内部错误 |

**轮询任务状态**：
```bash
# 轮询直到 status 为终态（completed/failed/cancelled）
curl $RCODER/api/v1/apps/publish/tasks/019123456789abcdef

# SSE 实时进度（推荐，带 from_seq 断点续传）
curl -N "$RCODER/api/v1/apps/publish/tasks/019123456789abcdef/stream?from_seq=0"
```

---

### POST `/apps/{app_id}/publish` — 触发完整发布流程

build + prepare + activate + 等待确认，一步到位。适合简单场景（不需要在 build 和 activate 之间做人工检查）。

**请求体** `PublishBody`：同 build。

**响应** `HttpResult<PublishTaskData>`：返回发布任务，`kind=publish`。

## 发布版本接口

### POST `/apps/{app_id}/releases/prepare` — 预备发布

从指定 URL 下载制品包，校验 sha256 后入库。**不切流**——应用仍运行当前版本。

**请求体** `PrepareReleaseRequest`：
```jsonc
{
  "release_id": "rel-20260815-001",           // 调用方生成的发布 ID（幂等键）
  "url": "https://ci.example.com/build/app-v1.2.0.zip",
  "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "size_bytes": 10485760,                      // 制品字节数
  "retention": 5                               // 可选：保留份数（默认取全局策略）
}
```

**响应** `ReleaseInfo`（注意：此接口返回裸对象，不包 HttpResult）：
```jsonc
{
  "release_id": "rel-20260815-001",
  "sha256": "e3b0c44298fc...",
  "size_bytes": 10485760,
  "status": "Prepared",
  "created_at": "2026-08-15T10:30:00Z"
}
```

**幂等**：同 release_id + 同 sha256 + 同 size 重复 prepare → 直接返回已有记录。

**错误**：
| HTTP | code | 说明 |
|---|---|---|
| 400 | ERR_VALIDATION | 参数校验失败（sha256 格式、retention 越界、URL 非法） |
| 404 | ERR_APP_NOT_FOUND | 应用不存在 |
| 409 | ERR_CONFLICT | release_id 已存在但摘要/大小不一致 |
| 500 | ERR_BACKEND_ERROR | 下载失败/校验失败/存储 IO 错误 |

---

### POST `/apps/{app_id}/releases/{release_id}/activate` — 激活发布

切换 code 软链到新版本 + 重启应用。**进入 PendingStart 状态等待健康确认**。

**请求体** `ActivateReleaseRequest`：
```jsonc
{
  "readiness_timeout_seconds": 120  // 可选：等待新版本就绪的超时秒数
}
```

**响应** `ReleaseInfo`：status=PendingStart。

**错误**：
| HTTP | code | 说明 |
|---|---|---|
| 400 | ERR_VALIDATION | 参数校验失败 |
| 404 | ERR_APP_NOT_FOUND / release 不存在 / 制品包文件缺失 | — |
| 409 | ERR_INVALID_STATE | 另一 release 仍处于待确认状态 |
| 500 | ERR_BACKEND_ERROR | 切流/拉起/索引写入失败 |

---

### POST `/apps/{app_id}/releases/{release_id}/confirm` — 确认发布健康结果

**发布决策点**——你观察应用健康后告知 RCoder 结果。

**请求体** `ConfirmReleaseRequest`：
```jsonc
{
  "healthy": true,           // 健康结论
  "message": "健康检查通过"   // 可选说明（healthy=false 时记入 failure_message）
}
```

**响应** `ReleaseInfo`：
- `healthy=true` → status=Active（当前生效版本）
- `healthy=false` → 自动回滚到上一 Active + status=Failed

**幂等**：重复 confirm 已终态且结论一致 → 直接返回。

---

### POST `/apps/{app_id}/releases/{release_id}/abort` — 中止 pending 发布

**运维自救**——针对 `confirm(healthy=false)` 自身失败导致 pending 残留的死局。仅改索引，不做文件/运行时操作。

**请求体** `AbortReleaseRequest`：
```jsonc
{
  "message": "confirm 超时后手动中止"  // 可选中止原因
}
```

**响应** `ReleaseInfo`：status=Failed，pending_release_id 已清。

---

### GET `/apps/{app_id}/releases` — 列出发布版本

**响应** `ReleaseListResponse`：
```jsonc
{
  "active_release_id": "rel-20260815-001",
  "pending_release_id": null,
  "retention": 5,
  "releases": [
    { "release_id": "rel-20260815-001", "status": "Active", ... },
    { "release_id": "rel-20260810-002", "status": "Prepared", ... }
  ]
}
```

---

### POST `/apps/{app_id}/releases/{release_id}/delete` — 删除发布记录

删除非 active/pending 的 release（保留策略外的手工清理）。

**错误**：active 或 pending 状态不可删（409）。

## 完整发布流程 curl 示例

```bash
# 假设应用已创建（见 02-接口手册 POST /apps）
APP_ID=app-order-svc
RCODER=http://127.0.0.1:8090

# ── 方式 A：完整发布（一步到位）──
# 1. 触发发布（build → prepare → activate 一条链）
TASK_ID=$(curl -s -X POST $RCODER/api/v1/apps/$APP_ID/publish \
  -H 'Content-Type: application/json' \
  -d "{\"project_id\":\"$APP_ID\"}" | jq -r '.data.task.id')

# 2. SSE 监听进度
curl -N "$RCODER/api/v1/apps/publish/tasks/$TASK_ID/stream?from_seq=0"

# 3. 构建完成后自动进入 PendingStart → 轮询健康
curl $RCODER/api/v1/apps/$APP_ID/health

# 4. 确认
curl -X POST $RCODER/api/v1/apps/$APP_ID/releases/$(curl -s $RCODER/api/v1/apps/$APP_ID/releases | jq -r '.pending_release_id')/confirm \
  -H 'Content-Type: application/json' \
  -d '{"healthy":true}'

# ── 方式 B：分步发布（build 和 activate 之间做人工检查）──
# 1. 构建
curl -X POST $RCODER/api/v1/apps/$APP_ID/build \
  -H 'Content-Type: application/json' \
  -d "{\"project_id\":\"$APP_ID\"}"
# → 轮询任务完成，拿到制品 URL

# 2. 预备
curl -X POST $RCODER/api/v1/apps/$APP_ID/releases/prepare \
  -H 'Content-Type: application/json' \
  -d '{"release_id":"rel-001","url":"https://ci/app.zip","sha256":"...","size_bytes":10485760}'

# 3. 激活
curl -X POST $RCODER/api/v1/apps/$APP_ID/releases/rel-001/activate \
  -H 'Content-Type: application/json' \
  -d '{"readiness_timeout_seconds":120}'

# 4. 观察健康 → 确认
curl -X POST $RCODER/api/v1/apps/$APP_ID/releases/rel-001/confirm \
  -H 'Content-Type: application/json' \
  -d '{"healthy":true,"message":"v1.2.0 发布成功"}'
```

## 回滚

RCoder 的发布模型中**回滚 = confirm(healthy=false)**（自动回滚到上一 Active）或 `activate 上一 Active 的 release_id`（手动回滚）。

```bash
# 手动回滚到上一版本
PREV_REL=$(curl -s $RCODER/api/v1/apps/$APP_ID/releases | jq -r '.releases[] | select(.status=="Prepared") | .release_id' | head -1)
curl -X POST $RCODER/api/v1/apps/$APP_ID/releases/$PREV_REL/activate
# → 轮询健康 → confirm
```
