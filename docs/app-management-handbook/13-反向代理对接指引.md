# 13. 反向代理对接指引（nuwax-file-server 前置换层）

> 本篇面向实现 60000 端口反向代理的同事：分流规则、header 约定、路径对照与端口表。
> rcoder 侧（Rust）已就绪，**TS nuwax-file-server 可以不改代码**。

## 1. 总架构与端口表

```
Java/调用方 ──┬─ userApp 新接口 ────────────直接──> rcoder 主服务 8086
              │
              └─ 既有 TS 接口路径 ──> 反向代理 60000（顶替原 TS 端口，您实现）
                   ├─ 无 X-Service-Type header → TS nuwax-file-server 60001（老业务零改动）
                   └─ X-Service-Type: userapp  → rcoder 主服务 8086 同路径透传
```

| 端口 | 服务 | 说明 |
|---|---|---|
| 60000 | **反向代理**（您实现） | 顶替原 TS 端口；分流规则见下 |
| 60001 | TS nuwax-file-server | 挪位后继续服务老业务（无 X-Service-Type 的请求） |
| 8086 | rcoder 主服务（生产容器内） | file-server 路由已常驻合并（老路径移植版 + userapp 转发层）；本地开发为 8090 |
| 60000（开发容器内） | Rust file-server | 每个 app 的 UserAppBuilder 开发容器内部端口，rcoder 转发寻址，代理无需感知 |

## 2. 分流规则（代理核心逻辑）

```
if 请求带 header X-Service-Type: userapp:
    转发到 rcoder 主服务（8086），路径与参数原样透传（body 零解析）
else:
    转发到 TS nuwax-file-server（60001），完全透传
```

- **判断只看 header**，不解 body（multipart 上传在代理层不可解）；query 也不用。
- 带标记的请求必须同时带 `X-App-Id`（定位该 app 的开发容器，由 rcoder 消费）。
- **自定义 header 默认透传**（绝大多数代理实现如此；请确认您的实现不剥离开头为 `X-` 的头）。

## 3. Header 约定

| Header | 值 | 谁消费 | 说明 |
|---|---|---|---|
| `X-Service-Type` | `userapp` | 代理（分流）+ rcoder 拦截层 + 容器内 computer handler（workspace 切换） | userApp 业务场景标记；不传 = 老业务 |
| `X-App-Id` | `{app_id}` | rcoder（定位 per-app 开发容器，`X-App-Id` → UserAppBuilder） | Java 调 8086 的**所有** userApp 请求统一携带（新接口与代理转来的老接口都是） |

## 4. TS 老路径 ↔ userApp 能力对照（Java 复用既有调用时）

Java 用 TS 老路径 + 两个 header 调用（`cid` = `app_id`，`userId` 照传）：

| TS 路径（原样） | userApp 语义（容器内 workspace = `{userapp}/{app_id}`） |
|---|---|
| `/api/computer/get-file-list` `resolve-file` `search-files` | 文件浏览/检索 |
| `/api/computer/files-update` `upload-file` `upload-files` `generate-file` | 文件写入（multipart 同样零解析透传） |
| `/api/computer/import-project` `install-project` | 项目导入/依赖安装 |
| `/api/computer/execute-command` `get-logs` | 命令执行/日志 |
| `/api/computer/zip-workspace` `download-all-files` `init-project-template` `push-skills-to-workspace(-v2)` | 打包下载/模板/技能 |

userApp **独有**能力（TS 没有的新接口，Java 直接近打 8086，不经代理）：

- `POST /api/userapp/workspace`（创建项目显式入口：ensure 开发容器 + 建目录 + 注册 owner）
- `POST /api/userapp/dev/{start,stop,restart,build}` `GET dev/{list,logs}`（dev server 生命周期）
- `POST /api/userapp/build` + `tasks/*`（构建/任务/SSE）
- `POST /api/userapp/db/{dev,prod}/align-credentials`（PG 凭据对齐）
- `POST /api/v1/apps/{app_id}/start`（部署：url 轻量部署 + `auto_execute_sql`/`user_id`/`pg` 可选字段）

## 5.5 userApp 开发域终端/桌面代理（Pingora 侧，非 60000 反代范围）

```
Web 终端:  {Pingora入口}/userapp/dev/ttyd/{app_id}/{path}   → 开发容器 ws_terminal(17681)→ttyd(7681)
远程桌面:  {Pingora入口}/userapp/dev/vnc/{app_id}/{path}    → 开发容器 noVNC(6080)
语音:      {Pingora入口}/userapp/dev/audio/{app_id}/{path}  → ws* 6089 / 其余 6090
输入法:    {Pingora入口}/userapp/dev/ime/{app_id}/{path}    → IME(6091, WebSocket)
```

- 全部按 **app_id** 定位 UserAppBuilder 开发容器（前置 `POST /api/userapp/workspace`；未注册 404）；
- 与 computer 族（`/computer/*` 按 user_id 定位沙箱）对称；Pingora 入口 = 8088 / K8s NodePort 30435；
- 终端 cwd = 开发卷 `{USERAPP_WORKSPACE_ROOT}/{app_id}`（与 chat/file-server 同根）；
- Swagger：rcoder `/api/docs` 搜 `/userapp/`（dev 域五工具 + `/userapp/routes` 速查表）；
- 旧 devapps 裸端口代理已退役（基础设施端口暴露面随之消除）；免端口流量族固定拨 pingap 9080，专用工具入口承带协议语义。

## 5.6 userApp 运行容器终端/数据库控制台（部署后的生产环境）

```
Web 终端:  {Pingora入口}/userapp/prod/ttyd/{app_id}/{path}   → 运行容器 ttyd(7681) 直连
PG 控制台: {Pingora入口}/userapp/prod/pgweb/{app_id}/{path}  → 运行容器 pgweb(8081)
```

- 目标是 **`ServiceType::UserApp` 运行容器**（app-runtime 镜像——部署后的生产环境），
  供线上排障；与 5.5 的开发域入口（`dev` 段，定位 UserAppBuilder 开发容器）区分；
- ttyd **直连本体 7681**（运行容器无 agent_runner，不经 ws_terminal 17681 中间层），
  客户端 WebSocket 同样携带 `tty` 子协议；终端 cwd = 容器内 `/app`；
- pgweb 直连容器内 PG（5432，supervisor 恒起，数据持久于 app 的 RWX PVC）；
- **语义差异**：开发域未注册 → 404；运行域 **app 未部署/已停止 → 502**（确定性 Service
  名定位，K8s Pod 重建 DNS 自愈）；
- Swagger：rcoder `/api/docs` 搜 `/userapp/`；`/userapp/routes` 速查表含 prod 段。

## 5.7 DBX 数据库 Web GUI 两阶段代理（开发 + 生产）

```
开发阶段:  {Pingora入口}/userapp/dev/dbx/{app_id}/{path}   → 开发容器(UserAppBuilder) dbx-web(4224)
生产阶段:  {Pingora入口}/userapp/prod/dbx/{app_id}/{path}  → 运行容器(UserApp) dbx-web(4224)
```

- **DBX 是 60+ 数据库的全功能 Web GUI**（pgweb 的上位替代，两镜像 supervisor 恒起 4224，
  容器内 PG 已预置连接；也可连远端库）；开发/生产双入口 stage 段与应用流量族
  dev/prod 语义对齐；
- 代理**剥前缀直连 root 模式** dbx（同 pgweb 模式）：dbx 前端从 URL 运行时推断 base，
  API/WebSocket 调用自动拼回 `/proxy/{dev,prod}/dbx/{app_id}` 前缀——Java 侧按上式拼 URL 即可，
  无需额外 header；
- 鉴权：dbx 自带密码（**首次打开时在浏览器设置**，存容器内 dbx.db 持久卷）；
- **语义差异**：dev 阶段该 app 开发容器未创建 → **404**（先调 `POST /api/userapp/workspace`）；
  prod 阶段 app 未部署/已停止 → **502**；
- K8s 前提：dbx 4224 已随 Service builtin ports 暴露（UserApp Service + agent per-pod Service；
  存量 agent Pod 需重建后其 Service 才含 4224）；
- Swagger：rcoder `/api/docs` 搜 `/proxy/`；`/userapp/routes` 速查表含 dbx 段。

## 6. AI 开发对话（不经代理，Java 直调 8086）

`POST /computer/chat` body 可选字段 `service_type: "userapp"`（body 字段而非 header）+
`project_id` = `app_id`：路由到该 app 的开发容器，ACP agent 直接在开发卷 workspace
工作（代码生成直接落卷）。不传 `service_type` = 原 computer 沙箱对话，零扰动。

## 7. TS 侧是否需要改动

**可以不改**：带 `X-Service-Type` 的请求被代理分流后根本不会到达 TS。若同事希望在
TS 侧声明该 header 作为契约说明（接口文档标注），加上也无妨——不影响分流行为。

## 7.5 npm 独立分发形态（`@nuwax-ai/file-server-proxy`）

除 rcoder 主 pod / agent-runner 容器内嵌形态外，代理另有 **npm 包独立分发形态**
（面向 Electron 客户端 / 本地开发环境），与本章 K8s 部署形态的差异：

- **单 Rust 二进制**：npm 包 postinstall 从 OSS 下载（tag `file-server-proxy-v*` 触发
  CI 构建，`--features embed-file-server`），**内嵌 Rust file-server**（同进程
  task 绑 `127.0.0.1:8086`），不再依赖外部进程提供 rust 上游；
- **TS 自动安装**：npm 依赖 `nuwax-file-server`（**精确版本 pin**，升级只随代理包
  发版），由包 CLI 托管：无健康实例则以**随机端口**拉起（全局单实例语义不变——
  已有健康实例直接复用其端口）；
- **CLI 守护**：`file-server-proxy start|stop|status|restart`（`--policy
  userapp_split|all_rust|all_ts`，默认 `userapp_split` 即 §2 分流规则；
  `all_ts` 为 npm 形态独有的全量回退档）；
- 分流规则、header 契约与本章 §2/§3 **完全一致**（同一 Rust lib）。

注意：npm 形态不使用 nuwax-file-server 的 `cli.js start`（其 stdio pipe 转发导致
CLI 进程不退出，且停 CLI 会连带停 server），直接托管 `dist/server.js` 并写同语义
PID 文件——与其 CLI 生态（stop/status）保持兼容。详见包内 README。

## 8. 部署清单（您侧）

1. TS nuwax-file-server 挪到 60001（`FILE_SERVER_PORT=60001` env）
2. 反向代理监听 60000（分流规则见 §2）
3. 生产 compose/K8s：rcoder 镜像需含本批改动（file-server 路由常驻合并 + 释放 60000）
