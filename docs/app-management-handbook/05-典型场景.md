# 5. 典型场景

> 端到端剧本，含可直接复制的 curl。贯穿示例：一个 Java Spring Boot 应用。
> 前置：`export RCODER=http://127.0.0.1:8290`（按你的环境改；Compose 用 8090）。示例假设已装 `jq` 用于提取字段。

---

## 场景 1：部署一个 Java 应用并轮询就绪

最常用的链路：创建 → 拿 app_id → 轮询状态 → 拼出访问地址。

```bash
# 1) 创建（异步：立即返回，status 通常 Starting）
curl -s -X POST "$RCODER/api/v1/apps" \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "order-service",
    "image": "registry.example.com/order-service:latest",
    "command": ["java", "-jar", "/app/code/app.jar"],
    "env": { "SPRING_PROFILES_ACTIVE": "prod", "SERVER_PORT": "8080" },
    "resources": { "cpu": "1", "memory": "1Gi", "ephemeral_storage": "2Gi" },
    "ports": [ { "name": "http", "port": 8080, "expose_type": "Http" } ],
    "health_check": { "check_type": "Http", "path": "/actuator/health", "port": 8080 },
    "tenant_id": "tenant-a", "space_id": "space-1"
  }' | jq .

# 响应里取 app_id（形如 app-1a2b3c4d）
APP_ID=app-1a2b3c4d
```

```bash
# 2) 轮询状态，直到 status=Running（建议间隔 2~5s）
curl -s "$RCODER/api/v1/apps/$APP_ID" | jq '{status, phase, ready_replicas, message, conditions}'

# 失败时（status=Error）看 conditions[].reason 定位：
#   ImagePullBackOff / ErrImagePull → 镜像地址或 registry 权限问题
#   CrashLoopBackOff                → 应用启动崩溃，看日志（场景 7）
```

```bash
# 3) 拿访问地址（默认 Pingora：http 只给 path /proxy/{port}，Java 拼 RCoder 入口）
curl -s "$RCODER/api/v1/apps/$APP_ID" | jq '.data.access'
# {
#   "external": { "http": "/proxy/8080", "tcp": [] },
#   "internal": {
#     "domain": "rcoder-app-app-1a2b3c4d-svc.<ns>.svc.cluster.local",
#     "short_domain": "rcoder-app-app-1a2b3c4d-svc.<ns>",
#     "ports": [ { "name": "http", "port": 8080 } ]
#   }
# }
# Java 拼：<你的-RCoder-入口>/proxy/8080   （gateway 模式则 path=/apps/{id}，拼 gateway 域名）
```

## 场景 2：更新镜像版本（全量替换）

> ⚠️ update 是**全量替换**：想改 image 也得把 env/ports/health_check 等一并带上（完整 desired）。

```bash
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/update" \
  -H 'Content-Type: application/json' \
  -d '{
    "image": "registry.example.com/order-service:v2",
    "command": ["java", "-jar", "/app/code/app.jar"],
    "env": { "SPRING_PROFILES_ACTIVE": "prod", "SERVER_PORT": "8080" },
    "resources": { "cpu": "2", "memory": "2Gi", "ephemeral_storage": "2Gi" },
    "ports": [ { "name": "http", "port": 8080, "expose_type": "Http" } ],
    "health_check": { "check_type": "Http", "path": "/actuator/health", "port": 8080 }
  }' | jq '{status, phase, message}'

# K8s 会触发滚动更新；轮询观察 Starting → Running
```

## 场景 3：启动 / 停止 / 重启

```bash
# 停止（scale=0，资源保留，配置不变，重启快）
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/stop"   | jq '{status, replicas}'

# 启动（scale=1）
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/start"   | jq '{status, replicas}'

# 重启（rollout restart，触发 Pod 重建，常用于更新配置/清内存）
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/restart" | jq '{status, phase}'
```

> **stop vs delete**：stop 是 scale=0（资源还在）；delete 是拆资源（计算面没了，但数据默认保留）。临时停用用 stop，彻底下线用 delete。

## 场景 4：删除（保留数据）与"误删找回"

```bash
# 默认删除：只删计算面，保留 code/data/logs
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/delete" | jq .

# 确认 app 已不存在（404）
curl -s "$RCODER/api/v1/apps/$APP_ID" | jq '{code, message}'
# { "code": "ERR_APP_NOT_FOUND", ... }

# 确认数据还在（exists=true, is_orphan=true）
curl -s "$RCODER/api/v1/apps/$APP_ID/storage" | jq .
```

### ⚠️ 关于"误删找回"（重要：当前实现现状）

v2 设计文档 §5.4 设想："用同一 app_id 重新 `POST /apps`，存储目录还在，新应用自动挂回旧数据"。**但当前代码实现中，`POST /apps` 的 app_id 由 RCoder 自动生成（`Uuid::v4` 前 8 位），CreateAppRequest 不接受外部传入的 app_id**——所以"用旧 app_id 重建挂回旧数据"这条路**当前走不通**，新建会得到新 app_id、挂新目录，旧目录沦为孤儿。

**现状下的务实做法**：
- 第一道防线已生效：`delete` 默认保留数据，数据没丢，只是"脱离"了 app。
- 若确需找回：旧数据目录仍在工作空间（`apps/{旧app_id}/`），需联系运维将该目录内容迁移到新 app 的目录，或直接在新 app 里通过 `upload` 重新上传关键文件。当前无 API 直接"认领"孤儿目录。
- 该能力（create 接受外部 app_id / orphan 目录认领）是已知的设计待落地项。

```bash
# 彻底清掉这些残留数据（仅当 app 已 delete 时允许，否则 409）
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/storage/delete" | jq .
```

## 场景 5：清理孤儿存储（批量）

应用删了、数据没清，日积月累成孤儿。用存储对账接口清理。

```bash
# 1) 找出所有孤儿存储（有数据、无对应运行应用）
curl -s -X POST "$RCODER/api/v1/apps/storage/query" \
  -H 'Content-Type: application/json' \
  -d '{ "page": 1, "page_size": 50, "filters": { "orphan_only": true } }' \
  | jq '.data.items[] | {app_id, is_orphan, modified_at}'

# 2) 对每个孤儿（app 已 delete，storage/delete 不会 409）逐个清空
for ORPHAN_ID in app-aaaa1111 app-bbbb2222; do
  curl -s -X POST "$RCODER/api/v1/apps/$ORPHAN_ID/storage/delete" | jq -r '.code'
done
```

> 注意：`storage/delete` 会先查 app 是否存在，**存在则 `409 ERR_INVALID_STATE`**（保护在用数据）。所以只能清"已 delete 的 app"的残留。

## 场景 6：RCoder / Java 重启后对账

无状态引擎的招牌场景。RCoder 或 Java 重启后，用 `GET /apps/runtime` 重建一致视图。

```bash
# RCoder 侧：列出集群中所有托管应用（label 反查，无需任何本地状态）
curl -s "$RCODER/api/v1/apps/runtime" | jq '.data[] | {app_id, status, phase, ready_replicas}'
```

**Java 侧逻辑**（伪代码）：

```text
runtimes = GET /apps/runtime          # RCoder 现场重建的全部托管应用
db_apps  = SELECT * FROM apps         # Java DB 持有的全部 desired

for app in db_apps:
    if app.id not in runtimes:        # DB 有、集群没有
        POST /apps {app.desired}      # 重建（desired 由 Java 持有）

for rt in runtimes:
    if rt.app_id not in db_apps:      # 集群有、DB 没有
        POST /apps/{rt.app_id}/delete # 按业务策略删除或保留
```

> 数据侧同步用 `POST /apps/storage/query`（`orphan_only: true`）——与 `GET /apps/runtime` 互补，覆盖"应用 vs 数据"两侧。

## 场景 7：日志排查

```bash
# A) 容器 stdout/stderr 快照（排查已发生的问题）
curl -s "$RCODER/api/v1/apps/$APP_ID/logs?tail=200&timestamps=true" | jq '.data[-5:]'

# B) 文件日志（适用写文件不写 stdout 的应用，如 Spring Boot）
curl -s "$RCODER/api/v1/apps/$APP_ID/logs/file?path=logs/application.log&tail=200" | jq '.data[-5:]'

# C) 实时流（WebSocket，盯日志看）——用 wscat
wscat -c "ws://127.0.0.1:8290/api/v1/apps/$APP_ID/logs/stream?tail=100"
# 服务端逐行推送 LogEntry JSON；Ctrl+C 断开即停（后台 follow 任务自动终止）
```

## 场景 8：上传部署物（如 jar 包）

> ⚠️ **先后顺序约束**：`upload` 需要路径参数 `app_id`，而 app_id 由 `create` 生成。所以"先传代码再启动"在当前 API 下的标准流程是：**create（拿 app_id）→ upload → restart（让容器加载新文件）**。
>
> 若应用的启动命令强依赖 `code/app.jar`，create 时容器会因缺文件短暂进入 `Error`/`CrashLoopBackOff`——这是预期的，upload 完成后 restart 即恢复。

```bash
# 1) 已有 app_id（create 拿到）
APP_ID=app-1a2b3c4d

# 2) 上传 jar 到 code/ 目录
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/upload" \
  -F "file=@./app.jar" \
  -F "target=code/app.jar" | jq .

# 3) 列出确认
curl -s "$RCODER/api/v1/apps/$APP_ID/files?path=code" | jq '.data'

# 4) 让容器加载新文件（若 create 时已因缺文件 Error，这里恢复）
curl -s -X POST "$RCODER/api/v1/apps/$APP_ID/restart" | jq '{status, phase}'

# （可选）后续替换部署物：直接 upload 覆盖 + restart
#       curl -X POST "$RCODER/api/v1/apps/$APP_ID/upload" -F "file=@./app-v2.jar" -F "target=code/app.jar"
#       curl -X POST "$RCODER/api/v1/apps/$APP_ID/restart"
```

> 删除部署物：`POST /apps/{id}/files/delete` body `{"path":"code/app.jar"}`（app 根相对，有 path traversal 防护）。

## 场景速查表

| 我想…… | 用哪个接口 |
|---|---|
| 部署一个镜像 | `POST /apps` → 轮询 `GET /apps/{id}` |
| 改镜像/配置 | `POST /apps/{id}/update`（全量替换） |
| 临时停用 | `POST /apps/{id}/stop`（scale=0） |
| 重启 | `POST /apps/{id}/restart` |
| 彻底下线（保留数据） | `POST /apps/{id}/delete` |
| 彻底下线（连数据清） | `POST /apps/{id}/delete` + `purge:true` |
| 看运行状态 | `GET /apps/{id}` |
| 看所有托管应用（对账） | `GET /apps/runtime` |
| 按状态/ID 筛应用 | `POST /apps/query` |
| 看日志 | `GET /apps/{id}/logs`（快照）/ `/logs/file`（文件）/ `/logs/stream`（WS） |
| 上传/查看/删文件 | `/upload` / `GET /files` / `POST /files/delete` |
| 查残留数据 | `GET /apps/{id}/storage` / `POST /apps/storage/query` |
| 清残留数据 | `POST /apps/{id}/storage/delete`（仅已 delete 的 app） |
