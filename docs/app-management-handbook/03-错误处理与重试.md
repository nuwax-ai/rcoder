# 3. 错误处理与重试

> 面向 Java 调用方：错误码语义、HTTP 状态码映射、哪些能重试、怎么决策。
> **本文以代码实际行为为准，并标注与 v2 设计文档的差异**——这点很重要，照设计文档实现重试会踩空。

---

## 3.1 错误响应体

所有接口的错误与成功共用 `HttpResult` 结构，错误时：

```jsonc
HTTP/1.1 404 Not Found      // ← 状态码与 code 对应
{
  "success": false,
  "data": null,
  "code": "ERR_APP_NOT_FOUND",       // ← 业务错误码（机器可读，以此为准做分支）
  "message": "应用不存在: app-1a2b3c4d", // ← 人读信息（含上下文，可用于日志/展示）
  "tid": "abc-123"                    // ← 追踪 ID
}
```

> 🔑 **判断错误类型看 `code`，不要只看 HTTP 状态码**。同一 HTTP 状态码可能对应多个 code（如 400 对应 `ERR_VALIDATION` 和 `ERR_OPERATION_NOT_SUPPORTED`）。Java 的重试/分支逻辑应基于 `code` 字段。

---

## 3.2 错误码 → HTTP 状态码映射表

下表 **第一列是当前 app_manager 实际会抛出的错误码**（来自 `AppOperationError` 枚举的 7 个 variant）。

| 错误码 | HTTP | 触发场景 | 可重试 |
|---|---|---|---|
| `ERR_VALIDATION` | 400 | 参数缺失/非法：app_id 格式错、storage/ephemeral_storage 非法 Quantity、path traversal、Exec 健康检查、update 缺 image、分页参数越界 | ❌ 终态 |
| `ERR_OPERATION_NOT_SUPPORTED` | 400 | 操作不支持（当前 app_manager 未实际抛出，预留） | ❌ 终态 |
| `ERR_APP_NOT_FOUND` | 404 | 应用不存在（Deployment/容器 404）；`get`/`start`/`stop`/`restart`/`update` 找不到 app | ❌ 终态 |
| `ERR_FILE_NOT_FOUND` | 404 | 文件管理目标不存在（文件日志、delete 文件） | ❌ 终态 |
| `ERR_APP_ALREADY_EXISTS` | 409 | 创建时同名资源已存在 | ❌ 终态 |
| `ERR_INVALID_STATE` | 409 | 状态不允许操作：对**仍存在**的 app 调 `storage/delete` | ❌ 终态 |
| `ERR_BACKEND_ERROR` | **500** | 后端运行时/基础设施失败（K8s/Docker API 调用失败、API Server 不可达、RBAC 拒绝） | ✅ **可重试** |

### ⚠️ 与 v2 设计文档的差异（务必注意）

v2 设计文档 §12.2 还列了两个错误码，但 **app_manager 当前实现并未落地**：

| 设计文档错误码 | 设计 HTTP | 设计可重试 | **当前实际情况** |
|---|---|---|---|
| `ERR_IMAGE_PULL_FAILED` | 502 | ✅ | **未抛出**。镜像拉取失败（ImagePullBackOff）当前归入 `ERR_BACKEND_ERROR`（500） |
| `ERR_RESOURCE_EXHAUSTED` | 503 | ✅ | **未抛出**。集群资源不足/调度失败当前归入 `ERR_BACKEND_ERROR`（500） |

> **根因**：`service.rs::map_runtime_error` 把除 `ContainerNotFound` 之外的所有 `ContainerRuntimeError` 统一映射成 `AppOperationError::Backend`（→ `ERR_BACKEND_ERROR` / 500），没有区分镜像拉取失败和资源耗尽。`AppOperationError` 枚举里也没有这两个 variant。
>
> **对 Java 的影响**：
> - 你**收不到** 502/503，镜像问题和资源问题都表现为 `500 ERR_BACKEND_ERROR`。
> - 想区分"镜像拉取失败 vs 临时基础设施抖动"，**别靠错误码**，要靠 `GET /apps/{id}` 返回的 `status=Error` + `conditions[].reason`（`ImagePullBackOff` / `CrashLoopBackOff` / `ErrImagePull` 等）来诊断。
> - 这两个错误码是预留位，后续 RCoder 在 runtime 层补上细分后会启用，届时 HTTP 会变成 502/503。**建议 Java 侧的重试逻辑基于 `code` 而非 HTTP 状态码**，未来升级无需改代码。

## 3.3 可重试 vs 终态（retryable）

RCoder 提供 `is_retryable_code(code)` 作为错误码的固有属性判断（定义在 `shared_types_i18n::error_codes`）：

```rust
pub fn is_retryable_code(code: &str) -> bool {
    matches!(code, ERR_BACKEND_ERROR | ERR_IMAGE_PULL_FAILED | ERR_RESOURCE_EXHAUSTED)
}
```

- **可重试**（Java 可指数退避重发）：`ERR_BACKEND_ERROR`（瞬时 5xx/timeout）。*（`ERR_IMAGE_PULL_FAILED` / `ERR_RESOURCE_EXHAUSTED` 虽列为可重试，但当前 app_manager 不抛出。）*
- **终态**（重发无用，必须改请求）：`ERR_VALIDATION` / `ERR_OPERATION_NOT_SUPPORTED` / `ERR_APP_NOT_FOUND` / `ERR_APP_ALREADY_EXISTS` / `ERR_INVALID_STATE` / `ERR_FILE_NOT_FOUND`。

> 简言之：**当前 app_manager 抛出的错误里，只有 `ERR_BACKEND_ERROR` 一个是可重试的**，其余全是终态。

## 3.4 Java 重试决策流程

```text
收到响应
  │
  ├─ success=true  → 正常处理
  │
  └─ success=false → 取 code
        │
        ├─ is_retryable_code(code) == true  (当前只有 ERR_BACKEND_ERROR)
        │     │
        │     ├─ 是写操作(create/update)且涉及镜像 →
        │     │     先 GET /apps/{id} 看 conditions.reason:
        │     │       · ImagePullBackOff / ErrImagePull / InvalidImageName → 终态(镜像问题, 重试无用, 通知用户改镜像)
        │     │       · CrashLoopBackOff                   → 终态(应用自身崩溃, 查应用日志)
        │     │       · 否则(无明确 reason / API 不可达)    → 可重试, 指数退避
        │     │
        │     └─ 其他(纯读操作 / 无镜像嫌疑) → 可重试, 指数退避(如 1s,2s,4s,...,上限 30s)
        │
        └─ is_retryable_code(code) == false  → 终态, 不要重试, 按 code 处理:
              · ERR_APP_NOT_FOUND      → 若是读/操作: 可能被并发删除, 视业务决定是否重建
              · ERR_APP_ALREADY_EXISTS → 创建冲突, 改用 update 或换 id
              · ERR_INVALID_STATE      → storage/delete 时 app 还在, 先 delete 再清存储
              · ERR_VALIDATION         → 修请求参数(看 message)
              · ERR_FILE_NOT_FOUND     → 文件/路径不存在
```

**指数退避建议**：基础间隔 1s，倍率 2，抖动 ±20%，上限 30s，最多约 5–6 次。写操作重试前务必配合状态查询，避免对"镜像问题"这类终态空转重试。

## 3.5 常见错误场景速查

| 现象 | 可能 code | 排查方向 |
|---|---|---|
| 创建后一直 `Starting`，最终 `Error` | — （查 status 非 code） | `GET /apps/{id}` 看 `conditions[].reason`：`ImagePullBackOff`=镜像地址/权限；`CrashLoopBackOff`=应用启动失败，看 `/logs` |
| `GET /apps/{id}` 返回 500 | `ERR_BACKEND_ERROR` | API Server 不可达 / RBAC 拒绝。**不要误判为"应用不存在"去重建**（会误删在用资源） |
| `storage/delete` 返回 409 | `ERR_INVALID_STATE` | app 还在运行，先 `POST /apps/{id}/delete` 再清存储 |
| `upload` / `files/delete` 返回 400 | `ERR_VALIDATION` | target/path 越界（path traversal）或 app_id 格式非法 |
| `update` 返回 400 | `ERR_VALIDATION` | 多半是漏传 `image`（必填），或 Exec 健康检查 |
| 文件日志 404 | `ERR_FILE_NOT_FOUND` | path 写错或文件未生成；注意路径是 app 根相对（如 `logs/application.log`） |
| 创建返回 409 | `ERR_APP_ALREADY_EXISTS` | 同 app_id 资源已存在（极少见，app_id 是随机生成的） |

## 3.6 错误码定义位置（供 Java 侧建常量表）

- 错误码字符串常量：`crates/shared_types_i18n/src/error_codes.rs`（如 `pub const ERR_APP_NOT_FOUND: &str = "ERR_APP_NOT_FOUND"`）。
- HTTP 状态码映射：`crates/shared_types/src/model/app_error.rs::status_from_code`。
- 可重试判断：`crates/shared_types_i18n/src/error_codes.rs::is_retryable_code`。
- app_manager 的错误抛出点：`crates/rcoder/src/app_manager/service.rs`（`AppOperationError` 各 variant + `map_runtime_error` / `map_io_error`）。

> Java 侧建议维护一份 `code → {http, retryable, 处理策略}` 的常量表，与上述 Rust 定义对齐。后续 RCoder 补上 `ERR_IMAGE_PULL_FAILED` / `ERR_RESOURCE_EXHAUSTED` 细分时，只需在这张表加两行，调用代码（基于 code 分支）无需改动。
