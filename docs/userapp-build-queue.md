# UserApp 重复构建与等待

同 app 的新 Build 请求会接替较早的 Build：先在任务表的同一个短临界区登记并发出取消信号，再等待旧构建释放工作区和执行名额。DevStart/DevRestart 不被普通 Build 取消；构建锁覆盖其编译及启动交接，不保持到服务运行结束。

该规则沿用 BuildManager/BuildTaskStore 的进程内边界，协调同一 file-server 实例里的请求。本次没有增加跨进程或跨副本的构建调度协议。

## 状态与取消

- 受理响应包含 `task_id`；等待快照为 `pending`，`stage=waiting_for_build_slot`，日志说明正在等待执行名额。
- 真正编译时转为 `running`、`stage=building`。
- 取消立即打断等待；已经执行的命令，包括 pnpm 的 lockfile/ignored-builds 自愈安装，使用同一任务取消信号停止进程树。
- `cancelled` 是任务终态，不代表物理清理在同一瞬间完成。新构建等待旧进程收束；清理暂未确认时后台继续处理，只保留对应工作区的执行租约，不要求用户删除登记文件。
- 已确认进程退出后，单纯回执写盘重试不继续占用构建槽。其他 app 不被该 app 的清理锁阻塞；全局执行容量仍受配置限制。
- 任务终态仅发布一次，旧 worker 的迟到错误或成功不能覆盖 `cancelled`。

## 两个独立预算

| 配置 | 默认 | 含义 |
|---|---:|---|
| `USERAPP_BUILD_WAIT_TIMEOUT_SECS` | 3600 秒 | 同 app 占用及全局执行容量的等待上限；取消不需要等到上限 |
| `DEV_COMMAND_TIMEOUT_SECS` | 600 秒 | 每一条构建或安装命令的执行上限 |

配置文件对应 `userapp_build_wait_timeout_secs` 和 `dev_command_timeout_secs`。二者均为正整数秒。

等待超时只说明请求没有在预算内取得名额，不说明原任务卡死，不会终止仍正常执行的 dev 任务。等待预算不再通过“服务数量 × 单命令超时”推导：一次构建可能包括安装、自愈重试、组包和启动等阶段。

普通网页项目的 `try_start` 仍保持同项目占用/容量满时立即失败；上述等待语义仅用于 UserApp 等待式入口。任务表保留容量耗尽仍可在受理时拒绝，与执行 Semaphore 的短暂占满不同。

## Java 等调用方接入

调用方需要保留 task_id，通过现有任务查询或 SSE 观察真实终态，并支持等待阶段与取消。不能因为阶段为 pending 就认定构建失败。

目前本地 agent-platform 的轮询仍有约 40 分钟总上限，构建产物处理还有从任务创建计的 35 分钟检查。它们可能短于“等待 + 执行”的实际时间：调用方需将等待和执行预算统一配置或分别计时；本次 RCoder 修改不修改 Java 工程，也不宣称该接入已经完成。

Java 受理入口还存在 activeGuard。需要调用方核对重复 Build 是否被这一层提前拒绝；RCoder 内的自动接替通过，不代表经过 Java 的重复请求已能到达本接口。

若调用方坚持固定总预算，应该在预算结束时调用取消并继续确认终态，而不是仅把 Java 本地行标记失败、让 RCoder 任务继续无人观察地执行。固定总预算应由产品/调用方明确，RCoder 不为迎合旧轮询常量而偷偷缩短合法构建时间。
